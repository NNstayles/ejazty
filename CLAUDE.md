# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Project

**Ejazty** — a study and mock-exam app for the Iraqi theoretical driving licence exam, in Arabic, Kurdish (Sorani) and English. Expo SDK 54 · React Native 0.81.5 · expo-router v6 · TypeScript.

Routes live under `src/app/`, not a top-level `app/`. The `@/*` path alias maps to `./src/*`, and `@/assets/*` to `./assets/*`.

## Commands

```bash
npm start                          # dev server
npm run android | ios | web
npm test                           # jest (jest-expo preset)
npm run test:watch
npx jest src/features/exam/engine.test.ts    # one suite
npx jest -t "puts the weakest topic first"   # one test, by name
npm run typecheck                  # tsc --noEmit
npm run lint                       # expo lint
npx expo-doctor                    # dependency/config health, 18 checks
npx expo export --platform ios     # bundles the full module graph — catches
                                   # unresolved imports that tsc misses
npx expo install --fix             # realign deps to the SDK manifest
npx expo start --tunnel            # when a device can't reach the LAN IP
                                   # prompts to install @expo/ngrok on first use
```

**`expo-auth-session` and `expo-crypto` were removed on 2026-08-08, and should not come back without a caller.** Neither was imported anywhere in `src/`. `expo-auth-session` is the one worth naming: the OAuth flow in `features/auth/oauth.ts` is built on `expo-web-browser` plus `supabase.auth.signInWithOAuth` instead, deliberately and with the PKCE reasoning written out, so leaving an unused auth library in the manifest was an invitation to reach for it and end up with a second, uncommented OAuth path beside the one the redirect allow-list argument depends on. `expo-crypto` was never needed — `newAttemptId()` says in its own comment that it uses `Math.random` to avoid pulling in a crypto polyfill, which is right for a per-user dedupe key. `react-dom`, `react-native-web` and `expo-dev-client` also have no `src/` imports and were **kept**: the first two back `npm run web` and the third backs the development-build profiles in `eas.json`.

**`@expo/ngrok` is deliberately not a dependency.** It carried a stale `uuid` and is needed solely for `--tunnel`. Expo CLI installs it on demand at the prompt, so removing it costs one keypress the first time you tunnel.

**Source maps are not emitted, and this is measured rather than assumed.** `npx expo export` produces **zero `.map` files** on either platform and writes **no `sourceMappingURL` annotation** into the bundle — iOS exports a single Hermes `.hbc`, web exports plain JS, neither with maps. They are opt-in behind `--source-maps`, so there is nothing to switch off and no `metro.config.js` is needed to hold the line. `dist/` is gitignored. Re-measure with `find dist -name "*.map" | wc -l` if a release pipeline ever starts passing that flag; EAS uploads maps to its own service for stack traces, which is a different thing from shipping them to a device.

Worth knowing what the bundle *does* contain: `grep -o sb_publishable_ dist/_expo/static/js/ios/*.hbc` matches. The anon key is inlined by design — that is the premise the entire RLS model rests on, not a leak.

**`postcss` is pinned forward through an `overrides` entry.** `@expo/metro-config` asks for `~8.4.32`, which cannot reach the fix; the advisories (the worst a 7.5 arbitrary-`.map`-read via attacker-controlled `sourceMappingURL`) are all patched in 8.5.x. `overrides: { postcss: "^8.5.25" }` in `package.json` forces the minor bump without touching the `expo` pin, and it is verified: both `expo export --platform ios` and `--platform web` succeed — web is the one that actually exercises the CSS pipeline `global.css` goes through — and `expo-doctor` still passes 18/18. This is what took the tree from *1 high, 15 moderate* to **0 high**. Re-check the override at the next SDK bump; once `@expo/metro-config` ships a range that includes 8.5, delete it rather than carrying it forever.

**`uuid` is pinned forward through the same `overrides` entry, which cleared every advisory that existed when it was written.** (The tree is *not* clean today — see the `image-size` note below, which supersedes the "clean at 0" claim this paragraph used to open with.) This corrects an earlier note in this file which said the override must *not* be applied, on the reasoning that `xcode` asks for `^7.0.3` while the fix is `11.1.1` — four majors up, on the package that writes `.pbxproj` files during prebuild. That reasoning was plausible and it was wrong; it was never tested.

What is actually true, measured rather than assumed:

- **`xcode` is the only consumer of `uuid` in the entire tree** (`npm ls uuid --all`), so `overrides: { uuid: "^11.1.1" }` is precisely scoped rather than a blanket bump.
- **`xcode` touches exactly one uuid API**: `uuid.v4()` at `node_modules/xcode/lib/pbxProject.js:90`, whose result is immediately `.replace(/-/g,'').substr(0,24).toUpperCase()`. `v4()` is call-compatible across v7→v11 and uuid still ships a CJS build, so the `require('uuid')` at line 22 resolves unchanged.
- **Verified end-to-end on a real `.pbxproj`**: parse → mutate (`addPbxGroup` + `addFramework`, 6 uuids minted) → `writeSync` → reparse round-trips cleanly, 30 uuids, none malformed, all unique; and `generateUuid()` produces 5000 unique valid 24-char ids. A full iOS `prebuild` cannot be used as the check on Windows — it refuses with *"Run npx expo prebuild again from macOS or Linux"* — so exercising `xcode` directly is the available equivalent, and it is the same code path.

**All 15 advisories traced to that single root.** Every other entry — `@expo/cli`, `@expo/config`, `@expo/config-plugins`, `@expo/metro-config`, `@expo/prebuild-config`, `expo`, `expo-asset`, `expo-constants`, `expo-linking`, `expo-notifications`, `expo-router`, `expo-splash-screen`, `jest-expo`, `xcode` — was reported only as a transitive path *to* `uuid`, which is why one override cleared the lot.

The advisory itself was genuinely unreachable (a missing buffer bounds check in `v3`/`v5`/`v6` *when a `buf` argument is supplied*, and nothing here passes one), so this bought no real safety — but "unreachable" is a claim that rots the moment `xcode` changes, and a clean `npm audit` is worth more than a paragraph explaining why a dirty one is fine. Note that `npm audit --omit=dev` would **not** have demonstrated the dev-only argument anyway, because `expo` itself is a runtime dependency — trace with `npm ls <pkg>` instead.

Re-check both overrides at the next SDK bump; once the upstream ranges include the fixes, delete them rather than carrying them forever.

**`npm audit` currently reports 11 high, and there is no fix to apply. This is an accepted risk, re-measured 2026-08-08.** The paragraph above used to end "and `npm audit` is now clean at 0", which was true when written and is not now. Recording the measurement rather than the conclusion, because the conclusion is what rotted:

- **All 11 entries trace to one root**, exactly as the `uuid` round did. `npm ls image-size --all` gives the whole path: `expo` → `@expo/metro` → `metro` → `image-size@1.2.1`. The other ten — `@expo/cli`, `@expo/metro`, `@expo/metro-config`, `metro`, `metro-config`, `metro-transform-worker`, `@react-native/community-cli-plugin`, `react-native`, `react-native-reanimated`, `expo` — are reported only as transitive paths *to* it.
- **There is no patched release.** Both advisories (infinite loops in the ICNS and JXL/HEIF parsers, DoS) are ranged `<=2.0.2`, and `npm view image-size version` is **2.0.2**. An `overrides` entry cannot fix this the way the `postcss` and `uuid` ones did; there is nothing to pin forward to. Re-check with `npm view image-size version` rather than assuming — this changes the moment upstream publishes.
- **`npm audit`'s own `fixAvailable` proposes `expo@53`**, a major *downgrade*, which is the same trap the `uuid` round produced (`expo@46`) and must not be taken. See the SDK pin below.
- **It is not reachable from a device.** `image-size` is used by the *Metro bundler* to read image dimensions at build time; nothing in the shipped bundle calls it. Exploiting it means feeding a malicious ICNS/JXL/HEIF file into your own build, which makes it a supply-chain question about `assets/` rather than a runtime one — and every file in `assets/exam/` and `assets/signs/` is JPEG or PNG produced by this project's own re-encode step.

Worth stating the general lesson, since this file leans hard on written invariants: **a documented measurement decays, and one that decays silently teaches the next reader to verify nothing.** The `uuid` note was scrupulous about being "measured rather than assumed" and still ended up asserting a number that had stopped being true. Re-run `npm audit` when touching this section rather than trusting the paragraph above it.

`npm audit fix --force` must still never be run, for the reason it never could be: it reads the `expo` pin as the thing to change. If an advisory ever *does* have a reachable fix, pin the specific transitive package with an `overrides` entry and verify it through the full sequence below, the way both current overrides were.

**Full verification, in order:** `npm test` → `npm run typecheck` → `npx eslint src` → `npx expo export --platform ios` (proves the module graph resolves) → `npx expo-doctor`.

**`npx expo export --platform web` currently fails, and it is not a regression in this project's code.** Measured 2026-08-08: it dies at 87% of the static-render pass with `TypeError: dependencies is not iterable` from `metro/src/DeltaBundler/buildSubgraph.js:16`, bundling `expo-router/node/render.js` — the SSG entry that `web.output: "static"` in `app.json` selects. It reproduces with the dependency tree in any state (confirmed by uninstalling and reinstalling unrelated packages), so it is a Metro/expo-router interaction rather than anything here.

Two consequences. **Use the iOS export as the module-graph check**, which is what the line above now says — it bundles the same `src/` graph and catches the unresolved-import case that `tsc` misses. And **the `postcss` note above is stale where it cites a passing web export as its evidence**: that verification was real when it was written and cannot be re-run today. The override still holds on the iOS side and `expo-doctor` still passes 18/18, so there is no reason to remove it — but if the web target is ever revived (it is a dev convenience today; EAS builds iOS and Android only, and there is no web deploy config in the repo), re-verify the CSS pipeline then rather than trusting that paragraph.

## Tests

559 tests across thirty-one suites, run under the `jest-expo` preset. **A full run takes about ten seconds.** It used to take around three minutes, and the five suites that accounted for nearly all of it — `learn/entries`, `progress/attempts`, `content/registry`, `learn/sections` and `exam/engine` — each ran 2 min or more because they assert against the *shipped* bundle rather than fixtures and pay to load it. That cost was documented here as the price of the guarantee and not a bug to optimise away, and that was half right: the guarantee is worth keeping, but the price was not the bundle, it was the artwork behind it. Re-encoding the exam pictures (see Content status) took the same five suites to 6–9 seconds each without changing a single assertion, because what they were paying for was `jest-expo`'s asset transform reading 48 MB of PNG on every run.

Worth drawing the general lesson, because it is the same number in three places: the bytes those suites were waiting on are the bytes Metro bundles, and the pixels behind them are what the device decodes while a learner scrolls. A suite that is slow for a reason nobody can name is worth measuring rather than accepting. There is no renderer test — everything covered is pure logic or data, which is where the failures that a learner cannot see for themselves live.

That constraint is also why the direction rules were made *pure*. A mirroring bug is only visible to someone who switches the app to Arabic and looks at it, so anything the suite can reach has to be extractable from a component: `directionFor` and `choiceMarker` exist in that shape deliberately, and are the right place to put the next rule of this kind.

- **`features/exam/engine.test.ts`** — grading arithmetic, the pass mark, the derived-question ceiling, and `compareAttempt`'s same-mode rule. Asserted against the *shipped* pool rather than fixtures, so editing `data/official/` and shifting the pool out from under `buildExam` fails here. One test pins `PASS_THRESHOLD` to the answer the bank gives for `q-pass-mark`, so the app cannot teach 80% while grading at something else.

  The `questionsToGrade` block pins **both halves** of the open-practice rule, because they are load-bearing in opposite directions: a fixed-length paper must keep marking what was skipped (the real test does), and open practice must not, or finishing it reports 8% for a session that went well. A version that filtered everywhere would silently turn every mock into a "questions I felt sure about" score, and a version that filtered nowhere puts open practice back to having no ending at all.
- **`content/registry.test.ts`** — runs `validateBundle` over the merged bundle as a hard failure. It already ran on dev boot, but only as a `console.warn`, in a build nobody ships. Also checks that all three languages are filled in on every localised field (a missing one falls back to English *silently* through `pick`), and that nothing unverified or `reference`-sourced can reach `examPool()`. The `study notes` block adds two the flat scan cannot reach: a note's `points` is an array of `Localized`, which the field walk steps straight past, and a note claiming a ministry `document` must carry a `locator` — its Arabic is written rather than verbatim, so the question numbers are the only way back to the page.

  The `duplicate questions and their pictures` block is the one that took a hand audit to write and should not be weakened casually. **Question identity is stem + choices + picture, and nothing shorter is a duplicate test at all**: the bank legitimately repeats a stem — sixteen right-of-way questions all ask "who has right of way in this picture?", six engine-bay photographs all ask which indicated part is which — and what tells them apart is the artwork. Measured: dropping the image component from the identity produces **6 false collisions**, so that component is what the test rests on. Four rules are pinned, all four mutation-checked by planting a violation: no question asked twice, no two questions with one stem and opposite answers (this is what keeps picture question 150's contradiction from being re-added — see Content status), every picture used by exactly one question, and every question whose stem names a picture carrying one. That last one lists `q-stop-line-meaning` as the single deliberate exception rather than widening a regex around it, so a *second* such question fails rather than slipping through.

  Note the picture rule is deliberately narrower than "no image used twice anywhere": a study note is routinely written about the very picture a question asks — that pairing is what `data/study/priority-pictures.ts` is *for*, and there are 62 such pairs. What must not happen is one picture standing in for two different questions.
- **`features/progress/question-stats.test.ts`** — per-question performance, which is what the mistake drill draws from. Three rules carry it and all three fail *silently*: the **owner boundary** (one person's record of which questions they keep failing must not greet the next account on the phone — the attempt cache's rule, same reasoning); the **answered-only rule** in `mergeAttempt`, because a timed mock grades the questions time ran out on and recording those as mistakes fills the drill with material the learner never saw; and **`weakestFirst`'s ordering**, which *is* the feature — a drill in the wrong order is still a plausible list of questions. Mutation-checked in four directions, each failing exactly one test: inverting the owner check, dropping the answered-only filter, ignoring `lastCorrect` in the ordering, and making `clearAccountQuestionStats` clear unconditionally.
- **`features/progress/attempts.test.ts`** — the owner boundary, the offline fallback, and the guest/account split on sign-out. All three fail silently in manual testing: you would have to sign in as two different people on one device, pull the network at the right moment, or practise as a guest and then go and register, to notice. AsyncStorage uses the official mock; Supabase is a hand-built double for the `upsert` and `select(...).eq(...).order(...).limit(...)` chains.
- **`features/notifications/reminders.test.ts`** — that the settings toggle **fails closed**, the mirror image of the CAPTCHA seam below. Every native call it can reach is restricted in Expo Go, and a rejection leaves the switch showing ON with nothing scheduled behind it *and* escapes unhandled, because the screen calls it with `void`. i18n is initialised in `beforeAll`: reminder text is baked in at schedule time, so this module reads i18n directly, and i18next throws rather than falling back when it has not been.
- **`features/notifications/schedule.test.ts`** — when reminders fire. Date arithmetic reaching three days ahead, and not one of its failure modes is observable from the app: a slot planned into the past never arrives, a dropped draw record repeats a message already delivered, a suppression rule one day too wide empties the queue for anyone who meets a goal. Reaching any of it by hand means moving the device clock. See Notifications.
- **`lib/haptics.test.ts`** — the haptic vocabulary, and the two rules in it that are invisible. `gives nothing away in a mode that does not reveal the answer` is the load-bearing one: a haptic that distinguished right from wrong inside a timed mock would leak the answer on every question with nothing on screen changing. It asserts the two branches are identical *to each other*, since any difference is the leak. The preference gate is the other — a switch that silently does nothing, or one that turns the feature off and leaves a call site tapping.
- **`features/notifications/routing.test.ts`** — where a tapped reminder goes. Both halves fail *open* when they break, which is what earns the tests: a `destinationFrom` that stopped validating returns the right answer for every notification this build schedules and misbehaves only on the one input nobody can produce by hand — a payload queued by a previous build and tapped after an upgrade. A `mayNavigateFrom` that always said yes looks identical everywhere except mid-attempt, where it discards a paper silently. See Notifications below.
- **`theme/typography.test.ts`** — the Arabic line-height floor and the direction rule. Both are invisible to a suite that only renders Latin, and invisible to a reviewer reading a diff that lowers a line height by two points. It has already earned itself twice: it caught `Math.round` rounding *below* the floor it was enforcing (19pt `heading`, 33 against 33.25), and it fails if `forceRTL(true)` is reinstated — which would silently put the app back to drawing one direction while the native flag claimed another, now that the restart notice that used to admit it is gone.
- **`features/auth/auth.test.ts`** — credential rules and the Supabase error-code mapping, including that a raw English `error.message` can never reach the screen. Also pins `MAX_NAME_LENGTH` to 80, because that constant is coupled to a CHECK constraint that can abort a signup (see Auth below).
- **`features/auth/captcha.test.ts`** — the CAPTCHA seam, and specifically that it **fails open**: no provider, a throwing provider, or one that never settles must all still let the request reach GoTrue. Failing closed here would lock every user out of a correctly configured project because a widget did not load. Also asserts the race timer is cleared — an uncleared one leaks a handle per auth attempt.

- **`features/auth/reauth.test.ts`** — the gate in front of password change, email change and account deletion. Everything asserted there fails *open* when it breaks, which is what earns the tests: a `reauthenticate` that forgot to call `signInWithPassword` at all would be indistinguishable from the app, every screen would keep working, and the gate would simply be gone. Pins that it verifies against the **session's** email rather than a caller-supplied one, that a missing session throws instead of falling through, and that the CAPTCHA token is attached.

- **`features/auth/identities.test.ts`** — which sign-in methods an account has, and therefore whether the gate above can possibly be satisfied. Everything here is unreachable by hand today, because both OAuth providers are disabled — which is exactly the point: the gap it closes opens on a **config flip**, so the first provider-only account appears the moment somebody enables a provider in the dashboard and nothing in a code review sees it. The load-bearing assertions are the two no-evidence cases answering `true`: that direction is safe only because `hasPassword` is an affordance rather than a gate, and if anyone ever routes an authorisation decision through it those two become the bug. Mutation-checked: returning true unconditionally fails 2.

  It also pins the **local backoff**, and the load-bearing assertion there is `stops reaching Supabase while locked out` — a version that counted failures but still forwarded every request would look identical from the app and bound nothing. The rest of that block holds the line against the two ways a rate limit gets deleted for being wrong rather than for being useless: a correct password must never consume budget, and a lockout must expire rather than stranding the owner. `fails open when the backoff store is unreadable` is deliberate and matches the CAPTCHA seam — a storage glitch must not lock someone out of their own password change, and an attacker gains nothing, because GoTrue's per-IP limit still applies to every request that *is* forwarded.
- **`lib/secure-storage.test.ts`** — chunking, the stale-tail bug, the AsyncStorage migration, and the keychain accessibility class. Every failure mode here is invisible by hand: chunking only bites on a session large enough to split, a stale tail only corrupts a session that shrank, the migration runs once per install on the upgrade, and the accessibility class only shows up on a device restored from a backup. SecureStore is faked with an in-memory map so the tests assert round-trip behaviour rather than restating the call sequence; the accessibility constants are distinct sentinels so the assertions compare against `SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY` itself rather than restating a hardcoded enum value.
- **`features/auth/password-strength.test.ts`** — the new-password rules, and **the only suite here where over-strictness is asserted as hard as under-strictness**. A rule that rejects `correct horse battery staple` does not get tuned, it gets deleted, so the `accepts` block is load-bearing rather than padding. Mutation-checked in all four directions: dropping the base list, the structural rules or the identity rules each fail, and so does tightening `BASE_DOMINANCE` to something over-strict. Two of the original identity tests used names that were *also* on the common list, so they passed via the wrong code path and survived deleting the rule they were meant to pin — worth remembering when adding cases, because the list is large enough that an arbitrary name may well be on it.
- **`features/auth/recovery.test.ts`** — the recovery-link parser, which is the only part of password recovery testable without a device, a mail server and a live project. The cases that earn their keep are the ones where an error arrives *alongside* a usable-looking `code` or token pair. Also pins `redeemableLink`'s refusal of the implicit `tokens` shape, and that the code it rejects with maps to "request a fresh link" rather than to the generic message — the two live in different files and would otherwise drift apart silently.
- **`i18n/direction.test.ts`** — that `direction`, `paragraphAlign`, `inputAlign` and `writingDirection` stay in step. Not that Arabic is right-to-left, which nobody breaks: the failure this catches is **one of the four lagging**, which is what produced rows that flipped while their paragraphs stayed left-aligned. Each used to be derived separately at its own call site, and the alignment pair was one field until React Native's logical/physical split was traced (see i18n and RTL below).
- **`features/learn/entries.test.ts`** — that **no two cards in a Learn section read the same, in any of the three languages, no record appears in two sections, and every note that ships actually reaches a screen**. The first two were broken in the shipped app. Measured in English before the fix: the signs section was 181 cards with 106 distinct headings (69 read "What does this sign mean?", 7 "What does this marking mean?"), road priority was 29 of 79, and 16 records rendered twice — every priority sign in both Traffic signs and Road priority, every priority light in both Rules and Road priority. Neither is visible in a diff, and finding either by hand means scrolling several hundred cards in three languages keeping a tally. Rebuilding the tab out of study notes removed the *mechanism* that produced the collisions, since a note is titled by hand; the assertions stay because the failure has not gone anywhere — two notes written months apart can say the same thing, and the writer of the second is exactly the person who will not notice. `renders every study note that ships` is the one that earns its keep now: a note whose `group` is not one its section declares is dropped silently, and nothing else would say so.
- **`features/learn/sections.test.ts`** — that **nothing in the exam bank is material the Learn tab never teaches**. The bank is the app's largest asset by a wide margin and it used to be exam-only, so a learner could be graded on a question with nowhere in the app to read about it — and `mechanics` and `firstaid` were worse, since `EXAM_TOPICS` excluded them from graded attempts too: eighty-five transcribed questions shipped in the bundle that nothing in the app could reach. (That second half is now closed from the other side as well — `EXAM_TOPICS` covers every bank topic since 2026-08-08, pinned by `engine.test.ts`.) The rule is now checked one level up from the cards: every topic the bank carries is claimed by exactly one section, and `backs every claimed topic with notes that teach it` is what stops the map being satisfied by a section that renders nothing. Every assertion fails silently by hand, because a topic with no section renders as a Learn tab that simply looks finished — a screen cannot show you what it was never told about.
- **`features/exam/breakdown.test.ts`** — the result screen's per-topic split. Two cases carry it. `puts the weakest topic first`, because the ordering *is* the feature — the list is read as "study this next", so an insertion or alphabetical order would quietly point most learners at the wrong section — and `omits a topic the attempt never asked about`, because a `quick` exam is fifteen questions and can easily miss one, and a row reporting that as 0% sends a learner to revise the subject they were not tested on. Both render perfectly plausible lists when wrong, which is why nothing else would catch them.
- **`features/exam/choice-markers.test.ts`** — the answer markers, and specifically their coupling to `MAX_CHOICES_PER_QUESTION`. That bound lives in `content/schema.ts`; raising it to five is a one-line change in another file that would silently leave every fifth option labelled `5` in a list of letters.
- **`i18n/locales.test.ts`** — the one locale-file failure the type system cannot see. `ar.ts` and `ckb.ts` are declared as `TranslationShape`, so a *missing* key is already a compile error; a key that is present and **empty** is not. That is how `notifications.items.stopSign.body` shipped blank in all three languages — one reminder of thirteen, rendering title-only at one of four daily slots, in a feature that cannot be exercised in Expo Go at all, so nobody would meet it before a user did. `time.unknown` is the single deliberate exception and is listed by name rather than pattern-matched around, so a *second* empty string fails rather than joining it. Mutation-checked: blanking any reminder half fails 2.
- **`i18n/fold.test.ts`** — the search folding, and the two directions it can be wrong in. Under-folding was the shipped bug (see i18n and RTL below); over-folding is the way a fix like this becomes worse than none, so `leaves the letters Sorani treats as its own alone` is asserted as hard as the harakat cases. Both failures are *silent*: a search that returns nothing looks like a section with no match, and one that returns the wrong card teaches the reader to stop using it.
- **`features/progress/goal.test.ts`** — the daily goal, which is **entirely date-boundary logic** and therefore reachable by hand only by changing the device clock and relaunching. `rollOver` has to carry a streak across exactly one midnight and no more, and both failure directions are silent and opposite: always keeping it turns the streak into days-since-install, never keeping it means nobody ever sees a number above 1. `increments the streak once, on the answer that crosses the goal` is the other load-bearing one — incrementing on every answer past the goal reports one productive evening as a twenty-day streak. `rolls over at local midnight, not at UTC midnight` is why `localDayKey` exists in `lib/dates.ts` rather than being `toISOString().slice(0, 10)`; east of UTC the ISO form files a late-evening session under the previous day. Mutation-checked: forcing `kept` true fails 3. The `parseProgress` block is the same kind of unreachable: it pins that a tally stored under the pre-rename `answered` key is still read, which only a device that ran the previous build yesterday can exercise — dropping the fallback fails 2, one of them the streak carry.
- **`features/exam/goal-credit.test.ts`** — which answers move the daily ring. Small, and every way of breaking it renders a perfectly plausible screen: a version crediting every answer is *indistinguishable* from a learner getting them right, and one without the per-question cap is indistinguishable from anyone who never goes back to change an answer. `does not withdraw credit when a correct answer is changed to a wrong one` is asserted as hard as the other two, because it is the half most likely to be "fixed" into a tally that counts down while the learner works. See the daily goal section below.
- **`features/profile/avatar.test.ts`** — the profile picture's owner boundary, which is the same rule `attempts.test.ts` pins for exam history and fails the same silent way, except more visibly: showing one person's *face* on another person's account is not a subtle mistake. Also pins the sign-out asymmetry (an account's picture goes, a guest's stays — see below) and that a stored `file` containing a path separator is refused rather than resolved. Mutation-checked: making `isVisibleTo` return true unconditionally fails 2. It also pins `safeExtension`, which is the *write* half of the separator rule the read half already enforced — `File.extension` is `Paths.extname` over the whole URI, so a picker URI carrying a query string yields `.jpg?width=800`, and `setAvatar` used to interpolate that straight into a filename `parseCache` would then reject on read, rendering as a picture that silently never appears. Mutation-checked: reverting it to `raw || '.jpg'` fails 4. `isSupportedImageMime` is the same shape of rule one step earlier — `mediaTypes: ['images']` constrains the picker's *UI*, not what comes back, so a document or an undecodable file was copied in, recorded as the avatar, and then silently never drew, under a "photo updated" notice. It is **not** an upload filter and the test says so: nothing is uploaded, and a file in an app sandbox has no execution path. Both directions are asserted because only one is visible — an iPhone camera roll returns HEIC, and rejecting it would break the feature for every iOS user while looking like a picker that does nothing. Absent means accepted, deliberately, matching the CAPTCHA seam. Mutation-checked: dropping the regex anchors fails 1. The rest of the filesystem half is deliberately not covered — a test of it would assert that a mock of `expo-file-system` was called, which pins the call sequence rather than the behaviour.
- **`features/navigation/tabs.test.ts`** — where a horizontal swipe lands. See the tab-swipe section below; both rules it pins are invisible in the language you develop in.
- **`lib/supabase.test.ts`** — the two client settings that are one line from being reverted and that nothing on screen would report: `flowType: 'pkce'` (the supabase-js default is `implicit`, which puts a live session in the deep-link URL — see Password recovery) and `persistSession: false` on web. `authConfig` is a pure function of the platform precisely so this needs no client, no network and no `Platform` mocking.

An attempt sat at 23:00 and read at 01:00 is yesterday to the person who sat it, and elapsed-millisecond arithmetic calls it today for another twenty-two hours — a wrong answer in the one case a reader notices, reproducible by hand only inside a two-hour window after midnight.

## SDK 54 is pinned deliberately

Expo Go is versioned per SDK — a client only loads projects on its exact SDK. The target device runs the SDK 54 client, so upgrading the SDK breaks device testing until a matching Expo Go ships. Do not bump `expo` casually.

Consequence to remember: **expo-router v6 does not re-export the React Navigation theme helpers.** `DarkTheme`, `DefaultTheme`, `ThemeProvider` and `Theme` come from `@react-navigation/native` (an explicit dependency). They only moved into `expo-router` in v7.

**`@react-navigation/bottom-tabs` is an explicit dependency for the same reason** — `BottomTabBarProps` and `CommonActions` are needed to write a custom tab bar, and relying on expo-router's transitive copy is a resolution that can move under you. Declare it as **`^7.4.0`**, the range the SDK manifest asks for: `npx expo install` writes the exact installed version (`^7.18.x`), which resolves identically but fails `expo-doctor`'s version check.

`expo-image-picker` and `expo-file-system` back the profile picture. Both are in Expo Go, so neither breaks the workflow this SDK pin exists to preserve. `expo-file-system` is on the **SDK 54 `File`/`Directory`/`Paths` API** — synchronous (`file.copy(dest)`, `file.exists`, `file.delete()`), not the promise-based legacy one still available at `expo-file-system/legacy`.

## Supported OS versions — iOS 16, Android 8

The floor is **iOS 16.0** and **Android 8.0 (API 26)**, set explicitly through `expo-build-properties` in `app.json`:

```json
{ "ios": { "deploymentTarget": "16.0" },
  "android": { "minSdkVersion": 26, "compileSdkVersion": 36, "targetSdkVersion": 36 } }
```

Both floors are **higher than the SDK 54 defaults** (iOS 15.1, `minSdkVersion` 24), so they are a deliberate narrowing, not a formality — without this plugin the app would install on iOS 15 and Android 7. `compileSdkVersion`/`targetSdkVersion` 36 match the SDK 54 default (React Native for Android targets Android 16 / API 36 on this SDK); they are stated rather than inherited so a future SDK bump cannot move the target silently.

These values only exist in the native projects, which are **generated, not committed** (`/ios` and `/android` are gitignored — this is a CNG project). Changing them requires a new build; there is nothing to verify in Expo Go, which ships with its own floor. To check the Android side: `npx expo prebuild --no-install --platform android`, then read `android/gradle.properties`, then **delete `android/`** — leaving it converts the project to the bare workflow and `npx expo prebuild` also rewrites the `android`/`ios` npm scripts to `expo run:*`, which breaks the documented Expo Go flow.

API 26 is also the release that made notification channels mandatory, which `features/notifications/` already creates unconditionally — so the floor costs nothing there.

## Store submission

Five settings in `app.json` exist only for the stores. All five look like noise in a diff and four of them are *removals*, which is the hard kind to keep — nothing on screen changes when they are reverted, and the cost lands weeks later inside a review queue.

- **`ios.supportsTablet` is `false`, and turning it on is a product decision, not a flag.** It obliges iPad screenshots in App Store Connect and puts the app in front of a reviewer on an iPad. It also *injects* `UISupportedInterfaceOrientations~ipad` carrying **both landscape entries**, regardless of the top-level `orientation: "portrait"` — so flipping it silently gives a portrait-designed app (the floating tab bar, the 180pt splash mark) a landscape layout nobody has looked at. Verify with `npx expo config --type introspect` after changing it: the iPad orientation key appears and disappears with this one boolean.

- **`ITSAppUsesNonExemptEncryption: false` is what stops every submission stalling on the export-compliance question.** The app makes standard HTTPS calls to Supabase and nothing else, which is the exemption. Without the key App Store Connect asks by hand on each upload and the build sits unusable until someone answers.

- **`NSAllowsArbitraryLoads` is pinned `false`, and the default it overrides is `true`.** That is not a dev-only default: it comes from the base Info.plist template in `@expo/config-plugins` (`withIosBaseMods.js`, `getInfoPlistTemplate`) which is unconditional, so a CNG project ships it to the App Store unless it says otherwise. The `localhost` exception is kept — it costs nothing and keeps local tooling working. Note this is the app's *own* Info.plist and has no bearing on Expo Go, which is a separate app with its own.

- **`expo-secure-store` is configured with `faceIDPermission: false`**, which removes `NSFaceIDUsageDescription`. The plugin adds a boilerplate string — *"Allow $(PRODUCT_NAME) to access your Face ID biometric data"* — by **default**, so it appears without anyone asking for it. This app never gates SecureStore on biometrics (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`, no `requireAuthentication`), so that string declared a permission the app does not use, in Expo's words rather than the project's. Both halves are rejection material. If biometric gating is ever added, this becomes a *written* purpose string, never the default.

- **`android.allowBackup` is `false`, and the default it overrides is `true`.** AsyncStorage is unencrypted on both platforms, and left backupable it is restorable — which matters for two entries in it specifically rather than for the study data: `ejazty.auth.biometricLock` (restore an old copy and the app lock is off) and, until it moved to the keychain, the re-auth lockout counter. Both exist to bound somebody holding the phone, and a backup restore is precisely that person's move. The session was never at risk either way — it is in SecureStore, encrypted with a Keystore key that is not backed up, which is the same reasoning `WHEN_UNLOCKED_THIS_DEVICE_ONLY` applies on iOS.

  The accepted cost, stated rather than buried: a user restoring onto a new Android phone arrives without their local exam history and profile picture. That mirrors the iOS trade already documented for the keychain class, and the account's attempts are in Supabase regardless — it is a guest's that are genuinely lost. Verify with `expo config --type introspect` rather than by reading `app.json`: the value has to reach `android:allowBackup` in the merged manifest, and it does.

- **`WRITE_EXTERNAL_STORAGE` is in `android.blockedPermissions`.** `expo-image-picker` pulls it in; the app only ever *reads* a picked image and copies it into its own document directory, which is scoped storage and needs no permission. `READ_EXTERNAL_STORAGE` stays, because minSdk 26 means Android 8–12 devices genuinely need it to read the gallery. Check the effective list with `expo config --type introspect` rather than reading the plugin — it is the merge that matters.

**Two things are deliberately *not* set, and both would look like obvious wins:**

- **`ios.infoPlist.CFBundleLocalizations`.** Adding `["en", "ar", "ckb"]` is what makes the App Store product page list all three languages, and it is genuinely worth having. It is not applied because it also changes the app's effective localization, which is the input iOS uses to decide RTL for anything the platform draws — and this app deliberately keeps `I18nManager` flat and carries direction itself (see i18n and RTL). `allowRTL(false)` should hold the line, but "should" is not a measurement, and the last time direction was assumed rather than checked it shipped every paragraph against the wrong edge. Apply it with a device in hand, in Arabic, and look at the OS-drawn `Alert` and `Switch`.
- **The `aps-environment` entitlement** that `expo-notifications` adds. The app schedules **local** notifications only and needs no push capability, but removing an entitlement a plugin injects is fiddlier than it is worth. The visible cost is that EAS offers to create a Push Key during credential setup; declining it is correct and changes nothing.

**`eas.json`:** `submit.production.ios` deliberately carries only `appleId`. `ascAppId` and `appleTeamId` are omitted so EAS resolves them interactively on the first submit — a wrong value in either fails in a way that reads like an auth problem. Paste them in afterwards for CI. The Android half points at `secrets/`, which is gitignored: that JSON is an upload-capable Play private key.

**`channel` is set on all four build profiles while `expo-updates` is not installed, so it is inert.** Kept rather than deleted because it is correct the day OTA updates are added, and a channel added later to only some profiles is the harder mistake.

## Content layer — the central abstraction

`src/content/` is the seam between the app and the official ministry material. Screens and the exam engine read **only** from `registry.ts`; nothing imports files under `data/` directly.

- `schema.ts` — every content type extends `Sourced`, so `id`, a `SourceRef` (authority, document, locator) and a `verified` boolean are mandatory. An unsourced record is meant to be impossible to add without noticing. `validateBundle()` runs on dev boot and reports duplicate ids, bad choice counts, and questions whose `correctChoiceId` matches no choice.
- `registry.ts` — merges bundles (highest-trust first), then exposes derived views: `roadSigns`, `markingsAndLights`, `prioritySigns`, `dashboardLights`, `studyNotesFor(topic)`, `bankTopics` and `examPool()`.
- `data/official/` — transcribed ministry content. `data/study/` — the Learn tab's study notes. `data/dashboard/` — dashboard tell-tales.

**A `ContentBundle` has four kinds in it, and it used to have seven.** `Violation`, `TrafficRule` and `PriorityScenario` are gone; all three are `StudyNote` now. Keeping them apart bought nothing the note's `topic` field does not give, and it cost the thing the Learn tab was rebuilt to fix — a "Keep your distance" rule card and a "Speed and following distance" note in the same list is a duplicate a reader sees immediately and a type system never will. `TrafficSign` and `DashboardLight` stay distinct because they genuinely are: artwork catalogues, keyed by a `category` or a `colour` the screen groups and colours by, carrying labelled fields a reader looks up individually. `data/general/` is gone with them; its material was folded into the notes.

**`SourceRef.authority` records provenance.** `federal-moi` / `kurdistan-moi` are government publications; `reference` marks material that is accurate but *not* official. The Learn screen badges any record failing `verified && authority !== 'reference'` as UNOFFICIAL.

**As of 2026-08-03 nothing carries `reference`, and that label is a product decision rather than a transcription fact.** The dashboard lights, the general road-code material and the added first-aid content were relabelled `federal-moi` on request so the UNOFFICIAL badge stops appearing. None of it is transcribed from a ministry publication — the dashboard set comes from a published car-symbol guide, the rest from conventions common to every road code and from standard first-aid practice. Every file carries a prominent provenance note, and the `document` strings still name what the material actually is, so the real origin stays recoverable from the code. **Do not treat a `federal-moi` label alone as evidence a record came from the manual; check the source ref's `document` string and the file's provenance note.** The `reference` value stays in the union for future content, and the badge logic stays as the guarantee that anything added under it cannot borrow the manual's authority.

The invariant worth preserving: **`examPool()` only ever returns `verified: true` questions.** Placeholder content has been deleted from the app, but the filter stays as the guarantee — anything added later without `verified: true` cannot reach a graded attempt. Independently of that, the study and dashboard bundles export **no questions at all**, so relabelling their authority did not put them into graded attempts.

### The Learn tab is study notes, not the exam bank

**This is the shape of the tab and the thing most easily undone by a well-meaning change.** The Learn tab used to render the exam bank directly: ~430 multiple-choice questions, each card printing QUESTION / ANSWER / WHY. That solved a real problem — before it, the largest asset in the project was reachable only by being graded on it — but it produced a study tab that reads as a quiz which has given itself away, one fact per card, and the same fact restated by every question that happens to test it. Sixteen penalty questions answering "A fine" are one note, not sixteen cards.

So `data/study/` holds **`StudyNote`** records: a heading, a paragraph, and a short list of the facts a learner has to recall — limits, distances, orders of precedence. 159 of them across six sections, 64 carrying artwork. The bank is untouched: `examPool()` still draws on every one of those questions and the exam is unchanged.

Three rules were followed while condensing, and they are what keeps the tab free of the duplication it was rebuilt to remove:

- **One fact, one note.** The bank asks the same thing from several directions — five questions establish that overtaking is prohibited near a pedestrian crossing, four that parking on a bridge or in a tunnel is not allowed.
- **Rules say what to do; Violations says what it costs.** Every penalty figure lives in the Violations section. Printing the fine beside each rule would restate that whole section inside this one.
- **A note cites what it was condensed from.** Its Arabic is written rather than verbatim, so `source.locator` naming the question numbers (`س ٤٨، س ٤٩`) is the only way back to the page. `registry.test.ts` pins that any note claiming a ministry `document` carries one.

### The picture questions are content, and leaving them out was a mistake

The first version of this rewrite dropped every picture question on the reasoning that "Who has right of way in this picture? — Vehicle B" is exam drill rather than something to study. **That was wrong and it lost a quarter of the Road priority section.** The diagram *is* the content: a right-of-way rule stated in a sentence and a right-of-way rule recognised in a junction are two different skills, and the second is the one the test measures.

Three files exist to hold them, and they are what makes the Learn tab and the exam cover the same material:

- **`priority-pictures.ts`** — all 24 right-of-way diagrams as worked examples, each keeping the ministry's own picture, describing what is in it, and naming the rule from `note-priority-ranking` that settles it.
- **`signs-extra.ts`** — signs the exam asks about that the *signs manual* does not illustrate. The signs catalogue is transcribed from one publication and the question bank is another, so **Give way, the general-danger triangle, radar enforcement, the expressway pair, the 70-metre gap, the taxi rank and eight more had no card anywhere in the app.** They are notes rather than `TrafficSign` records because a catalogue card promises the manual's wording and these have the question guide's instead.
- **`rules-pictures.ts`** — the hatched-median and merge markings, plus the situations whose content is the picture: a child stepping out from between parked cars, the two ways of passing a motorcycle, a residential street with no signs on it.

**A caution that governs all of `priority-pictures.ts`:** the publication gives the answer and almost never gives the reason. Where the diagram makes the reason plain — a give-way triangle, a stop sign, one car going straight while the other turns across it — the note says it. Where it does not, the note states the situation and the answer *without inventing a rationale*, because a confident wrong reason is worse than none: a learner who memorises a rule that does not exist will apply it at a junction the guide never showed them. `note-priority-two-on-a-roundabout` is the clearest case and should stay as it is.

**Coverage was measured, not assumed.** `tools/`-style keyword sweep of all 430 questions against every note and catalogue card left 31 weak matches, each read by hand and confirmed to be a false positive of the matcher. Re-run that sweep after adding a topic.

**The sweep is committed now, and re-measured on 2026-08-08 in English rather than Arabic — which found two real gaps the Arabic sweeps had not.** `scripts/coverage-sweep.py` reads `audit-dump.json`, written by `src/content/dump-content.test.ts`:

```bash
DUMP_CONTENT=1 npx jest src/content/dump-content.test.ts   # writes audit-dump.json (gitignored)
python scripts/coverage-sweep.py 0.30                      # weak matches, weakest first
```

The dump is a test rather than a script because the bundle `require`s its artwork, so it only loads through `jest-expo`'s asset transform; it is **opt-in behind `DUMP_CONTENT=1`** so `npm test` and CI do not write a 400 kB file on every run. It dumps English deliberately, for the vocabulary reason described just above: an Arabic sweep reports a translation difference as a coverage gap, which is what buried these two.

**Both gaps were the same shape — a *warning* sign whose prohibition and mandatory counterparts were already in the catalogue while the warning itself was missing.** `note-sign-bicycle-crossing` (ص س ٣٢) is the sharper one: its question's two distractors are "Bicycles prohibited" and "A road reserved for bicycles", which are exactly `sign-no-bicycles` and `sign-mandatory-cycle-path` — so a learner who studied every card the app had was being taught **both wrong answers and never the right one**. `note-sign-farm-animals` (ص س ١١١) is the same against `sign-no-animals` and `sign-mandatory-animal-path`. Both notes therefore name their neighbours rather than describing the triangle alone, because the distinction is what the question measures.

The reverse direction was swept too and has no defects: notes with no exam counterpart are the *deliberate* enrichment — First aid at 8 notes against the bank's 3 questions, and the violations described in kind where the bank gives no figure. Learn teaching more than the exam asks is correct; the scores in that direction also read low as a metric artifact, because a note is longer than the question it teaches.

**Re-measured independently on 2026-08-07 and it holds — but note what the sweep is actually measuring.** A fresh token-overlap sweep, folded for harakat and searching *every* section rather than the question's own topic, left 47 weak matches; all 47 read by hand and all 47 false positives. The reason is worth knowing before anyone reruns this and panics: **the notes and the bank use different Arabic vocabulary for the same thing.** The bank is transcribed verbatim and prints colloquial and transliterated Iraqi forms — `الباتري` for the battery, `خزان سائل البريك` for the brake-fluid reservoir, `الاجتياز` for overtaking, `الاستدارة الدائرية (فلكة)` for a roundabout — while the notes are written in Modern Standard Arabic (`البطارية`, `خزان زيت الفرامل`, `التجاوز`, `الدوّار`). A word-overlap matcher reads that as a coverage gap and it is a translation difference. The same applies to figures: notes print `٦٠` where the bank prints `60`.

Two practical consequences. First, **search the concept, not the string**, when checking whether something is taught. Second, this vocabulary split is exactly why `foldForSearch` folds Arabic-Indic digits — see i18n and RTL below.

The same pass re-checked the 62 note↔question artwork pairs the same way, with the same result: every apparent mismatch is the note titling the picture as something to learn (`كرة ثم طفل` — "a ball, then a child") where the bank answers the question asked about it (`الأطراف المحيطة بالشارع`). The pairings are sound.

Two catalogues survive as catalogues, because they are genuinely reference material rather than prose: the 111 signs and the 94 dashboard tell-tales, both with artwork and both with labelled fields.

**The coverage rule survived the rewrite and is the thing to preserve.** It used to read "every bank question appears in exactly one Learn section". It now reads: every topic the bank carries is claimed by exactly one section (`SECTION_BANK_TOPICS`), and a section may only claim a topic if it has notes teaching it. Both halves are in `sections.test.ts`. Without them, adding a topic to `QuestionTopic` puts the app straight back into the state it shipped in, where `mechanics` (82 questions) and `firstaid` (3) were transcribed, validated, bundled, excluded from `EXAM_TOPICS` — and dead.

`entries.test.ts` holds the level below it: **every note that ships actually reaches a screen.** A note whose `group` is not one its section declares is dropped by `buildGroups` silently, and that is a typo away at all times.

### Sections, groups, and no record with two homes

`SECTION_IDS` and `SECTION_GROUPS` in `features/learn/sections.ts`, both total `Record`s so a new section is a compile error until it states its answer.

- **`SECTION_IDS` is in study order and drives the home screen directly** — signs, rules, priority, violations, mechanics, dashboard, firstaid. The tiles are derived from it rather than listed separately, so a section cannot be added and then silently left off the home screen.
- **`LearnSectionId` is an alias of `NoteTopic`**, declared in the content schema. A note cannot be written for a section that does not exist, and a section cannot be added without the content layer knowing.
- **Groups are display order and the note names its own.** Catalogue cards are bucketed from the data (`category`, `colour`); a note carries `group: string`, and `entries.test.ts` pins that the name is one its section declares. Making that a compile error would mean putting display order into the content layer, which is the trade being made.
- **`buildGroups` walks `SECTION_GROUPS`, not the data.** Reference material first in the sections that have both, because the catalogue is what the notes are written about. An empty group drops out rather than rendering as a sticky heading over a gap.

**The road-priority section lists no sign cards.** Every priority sign is also a road sign and every priority light is also a traffic light, so it was putting 16 records on screen twice. The catalogue won — a "Traffic signs" section missing STOP and Give Way is worse than a priority section holding only its ranking and its situations. `prioritySigns` stays exported from the registry because `priority` is a real property of a sign; it is simply not a section boundary.

**`features/learn/entries.ts` holds the builder, outside the route directory.** Same reason as `sections.ts`: the screen imports `expo-router` and `expo-image`, there are no renderer tests, and the guarantees worth having here — no duplicate headings, no record in two sections, no note that never renders — are exactly the ones nothing could otherwise reach.

**`buildGroups` is cached, and the cache is keyed on the translator.** The work is not small and it happens at the worst possible moment: a section screen calls it *while mounting*, which is during the push animation, and the signs section flattens 111 catalogue records, picks three localised fields off each, and folds the joined result through `foldForSearch` — an NFKC normalisation plus five regex passes over the whole string. None of it depends on anything that moves: the content bundle is a static import, so for a given section and language the answer is always the same array. The `t` key is a `WeakMap` rather than part of a string key because `entries.test.ts` calls the builder with a fresh translator per case, and a cache that ignored `t` would hand the second call the first one's headings. **Callers must treat the result as frozen** — the screen filters into fresh objects and `SectionList` only reads, which is what makes this safe.

**Never put `gap` on a virtualised list's `contentContainerStyle`.** This was the road-priority scroll jump, and it had survived two earlier rounds of tuning aimed at the artwork. `VirtualizedList` keeps a frame table of cell offsets built from each cell's own `onLayout`, and for a cell it has never measured it approximates: `index * averageCellLength`, where the average is over measured cell **heights**. Container `gap` is not part of any cell's height — it is space the flex container inserts between them — so every unmeasured row was estimated one gap short, the error compounding with the index (~600pt across road priority's 38 rows), and the moment those cells mounted and reported their real positions the list corrected its content offset in one step. That correction is the jump. It bites worst where rows are tallest, because the fewest are measured and the most are being guessed at. The spacing now lives inside the measured cells in all three lists — `learn/[section].tsx`, `exam/result.tsx`, `question-navigator.tsx`. `gap` *inside* a cell is fine; it is only the container's that is invisible to the frame table.

**The section list's virtualisation settings are tuned against the artwork, so they move when it does.** `maxToRenderPerBatch`/`updateCellsBatchingPeriod` were raised to 7-per-30ms to outrun the PNG decode; with the artwork re-encoded they are back at 5-per-50ms, because the cap cuts both ways — a batch is rendered and committed in one go, and seven road-priority rows (a 160pt diagram plus a paragraph plus a bulleted list, each) in a single commit is a long frame, which during a fling is felt as the list lurching rather than filling. `windowSize` is untouched: it bounds how much stays mounted and was never the problem. `removeClippedSubviews` stays off for the reason it always was.

**`renderItem` wraps every row in `Animated.View` and switches only `entering`.** It used to return a bare card once the list had settled and a wrapped one before, which put a *different element type* at the same position — so the first re-render after `settled` flipped tore down the subtree and rebuilt it, dropping the mounted `Image` and re-attaching it. That is a card going blank and repainting at the exact moment the reader starts to drag. Reanimated reads `entering` once at mount, so `undefined` there is genuinely no animation rather than a suppressed one.

**The picture↔text pairing was audited and is sound.** Re-measured after the rewrite: 211 records carry artwork, no missing files, no image used by two records, no orphans in `assets/signs/` (111) or `assets/dashboard/` (94), and the `pic-NNN` ↔ locator mapping is strictly sequential with the 135–142 boundary matching the transcription notes. Spot-checked visually across every sign category. If a picture ever *does* look wrong, check the transcription JSON in `tools/question-transcriptions/`, not the screen.

**62 notes carry artwork, and the exam images among them were each checked against their caption before being attached.** The six engine-bay shots (`pic-135`, `pic-137`–`pic-141`) whose question is "what is the part indicated?", the 24 right-of-way diagrams, the signs the manual does not illustrate, and the situational photographs. The test for whether an exam image belongs in Learn is whether the picture is the content or merely illustrates a question — a diagram of a junction is the former, a photograph of a car with a question written beside it is the latter.

**Two notes were written and then deleted as duplicates, and the reason is worth knowing before adding more.** `note-sign-stop` and `note-sign-parking-place` duplicated `sign-stop` and `sign-car-park`, which *are* in the catalogue — a `grep` truncated by `head` was what suggested otherwise. `entries.test.ts` caught both on the Arabic heading. Check the full catalogue, not the first ten matches, before deciding a sign is missing.

## Exam engine

`features/exam/engine.ts` is pure (draw, shuffle, grade). `features/exam/exam-session.tsx` holds attempt state and is mounted in the exam **stack layout**, so an in-progress attempt survives navigation between the runner and the result screen.

- **Five formats.** `quick` 15 questions / 3 min, `medium` 25 / 5 min, `full` 45 / 15 min, `open` — the whole eligible pool, untimed, with the answer revealed as each question is answered — and **`drill`**, the mistake drill.

  **`drill` is selected rather than sampled**, and it is the only format whose availability changes as the learner practises. It draws up to `DRILL_SIZE` (20) of the questions *this learner* has answered wrongly and not since got right, weakest-first, from `features/progress/question-stats.ts`. `buildExam` takes `weakIds` as a second argument and returns early for it, sharing none of the derived-share arithmetic below — the ids arrive already ordered, and the *selection* preserves that order while only the survivors are shuffled, because shuffling first would hand back an arbitrary twenty of the learner's mistakes rather than their twenty worst. Ids are resolved against the live pool rather than trusted, so a stat naming a question edited out of the bank shortens nothing, and the selection is deduplicated defensively even though `weakestFirst` cannot repeat one.

  `canRunExam('drill', weakCount)` is false at zero and the card says so in its own words (`exam.drillEmpty`) rather than "not enough questions in the bank", which would be false as well as unhelpful — the bank is full, the learner simply has no mistakes on record. It is untimed with immediate feedback because it is revision rather than assessment, and its percentage is deliberately not comparable with a mock's; nothing joins them, since `compareAttempt` is same-mode only. `ExamModeConfig.questionCount` is `number | null`, where null means "draw everything"; `immediateFeedback` is true only for `open`, because revealing answers inside a timed paper changes what the score measures.

  The four mode cards on the exam home carry **no description line**. Each restated the two chips under it — "a longer set to test your consistency" above `25 questions · 5 min` — and four of them turned a list of four choices into a page of prose to read before choosing. Removed on the owner's request; the `*Desc` keys are gone from all three locales.
- **`questionsToGrade` decides what an attempt is marked on, and it is what gives open practice an ending.** For a fixed-length paper it is every question drawn: skipping one in a timed mock is a decision with a cost and the real test counts it, which is what `ExamResult.skipped` reports. `open` is different in kind — it draws the *entire* eligible bank, so `Next` reaches `Submit` only on the last of several hundred cards and the only real exit was Quit, which throws the attempt away. Grading the whole draw instead would report 8% for a session in which the learner answered forty questions and got thirty-four right, which is worse than no result at all.

  So open practice is marked on what was answered, and can be finished at any point from the question navigator. Two consequences to keep in view: an `open` percentage is **not comparable** with a mock's, because the learner chose which questions counted (nothing joins them — `compareAttempt` and the trend line are both single-mode, for this reason among others); and finishing with nothing answered would be a zero-length attempt, which grades 0% and which the `total > 0` CHECK on `exam_attempts` rejects outright. `finalise` refuses that case and the navigator's button is disabled behind it.
- `PASS_THRESHOLD = 0.6` — **an app policy, not the ministry's mark.** The publication passes at 80% and asks the pass mark as a question (`q-pass-mark`, س ٢٤). On 2026-08-05 the owner asked for both the grading threshold and that question's answer to read 60%, so `q-pass-mark` now offers ٦٠٪ where the source offered ٧٥٪ and marks it correct. That record carries a comment saying so — it is the only answer in the bundle that does not match the ministry's marking, and it should not be mistaken for a transcription slip. **A learner who passes here at 62% would fail the real test.** Three sites move together: this constant, `q-pass-mark`, and the CHECK in `20260806090000_pass_threshold_60.sql`; changing one alone makes every attempt fail the constraint and stop syncing, silently, because `pushAttempt` ignores failures by design.
- Questions carry **3 or 4 choices** (the official bank uses 3 throughout), one correct, enforced by `ChoiceSet` and `validateBundle`.
- **Exams draw from every topic the bank carries** (`EXAM_TOPICS` = `signs`, `rules`, `priority`, `mechanics`, `firstaid`), which widened on 2026-08-08 on the owner's instruction that the exam cover everything in the source. It used to be the first three, on the reasoning that a mock should mirror the official theoretical test — and the cost of that was invisible from every screen: 82 `mechanics` and 3 `firstaid` questions were transcribed, validated, bundled and taught in the Learn tab, and could never be asked. The pool went 456 → **541**.

  The trade, stated rather than buried: a mock is no longer a pure simulation of the real paper. Roughly a sixth of a 45-question mock is now vehicle upkeep and first aid, which the real test does not cover, so a percentage here reads slightly *low* against the real thing rather than slightly high — the safer of the two directions, and the one chosen deliberately.

  **Dashboard tell-tales stay out, and cost nothing to keep out:** `data/dashboard/` exports 94 catalogue records and **no questions at all**, so they have never been in the pool — the 111 derived questions are one per sign, from `sign-questions.ts` alone. If dashboard lights are ever given derived questions they need a topic of their own rather than joining one of these.

  `engine.test.ts`'s `leaves no transcribed topic unexaminable` pins `EXAM_TOPICS` against the shipped bank's own topic list, so narrowing it again fails rather than silently stranding questions; it is mutation-checked. The classification rule used while transcribing: behaviour in traffic is `rules`, the vehicle itself is `mechanics`, who-goes-first is `priority`, sign and marking meanings are `signs`.
- **`MAX_DERIVED_SHARE = 0.5` sets the share of auto-generated questions per attempt.** `Question.derived` marks the one-per-sign identification questions. There are 111 of them against 26 transcribed, so a uniform draw made a "full mock" ~24 sign cards and six real questions.

  **It is a target split, not a ceiling** — this is the thing to get right before editing `buildExam`. `Math.max(share, shortfall)` gives a paper *exactly* half derived questions whenever that many exist, and more only when the transcribed bank cannot fill its own half. Now that the whole bank is transcribed the shortfall arm never fires, and a 45-question mock is 23 derived / 22 transcribed. The share is still doing the same work from the other direction: without it, sign-identification cards would be a small minority of a 400-question pool rather than the half the official test warrants. If you ever want derived questions to fade out as the bank grows, the `Math.max` is the only line that needs to change.

  **`open` skips this entirely.** The share shapes a *sample*; open draws the whole pool, so there is nothing to balance and applying it would silently halve the practice set. `buildExam` returns early for it, and `engine.test.ts` pins that the open draw is exactly `examPool(EXAM_TOPICS).length`.

  Note the test (`caps auto-derived questions at the ceiling`) asserts only the upper bound, so it passes under either policy — it will not catch a change of split. Assert the exact count if that matters to you.
- Questions and choices reshuffle per attempt; timed modes auto-submit at zero.
- **`features/exam/question-navigator.tsx` is the whole paper at once**, opened from the position readout in the top bar. It exists because two separate problems were the same missing control. A 45-question mock could only be walked one card at a time, so revisiting question 6 before submitting meant thirty-nine taps of Back, and nothing said which questions were still blank until the submit dialog counted them and offered no way to act on the number. Open practice, meanwhile, had no ending (above). The finish action lives in this sheet rather than in the action row because it belongs beside the count of what is still blank — that count is what a learner needs in order to decide.

  Its cells report correct/wrong **only in a revealing mode**. In `open` the answer was already shown on the card, so the grid is a map of what to go back and re-read; in a timed mock it would be a live scoreboard the real exam does not give you, which is the same reason `immediateFeedback` is false there. Two mechanical details: it re-applies `direction` because it is a `Modal` (see the two places direction does not inherit), and its grid pads the data with invisible cells to a whole number of rows — `numColumns` lays a short final row across the full width, so a 15-question paper otherwise ends with three cells three times the size of the others.
- **Question artwork is tappable in all three places it appears** — the Learn catalogue, the session runner and the result review — through the same `ArtworkViewer`. It used to be zoomable only in Learn, which is the wrong way round: the six engine-bay photographs ask which *indicated* part is which and the right-of-way diagrams have to be read for which car is where, and the exam is where getting that right counts.
- `compareAttempt()` scores an attempt against earlier ones. It compares only within the **same mode** — a 10-question warm-up and a 30-question mock are not comparable, and a cross-mode comparison would report improvement that did not happen.

### The result screen answers "where", not just "how much"

`(tabs)/exam/result.tsx`. Three things were added on 2026-08-06, and each closes a gap that made the screen a verdict rather than a next step:

- **`features/exam/breakdown.ts` splits the attempt by topic**, weakest first, and each row links straight into the Learn section that teaches it. "30 of 45" is a number to feel bad about; "Traffic signs 14/15 · Road priority 4/12" is an instruction. The route is a one-liner because **a topic id *is* a Learn section id** — `LearnSectionId` aliases `NoteTopic` and `QuestionTopic` is a subset of it — which `sections.test.ts` keeps true. It is hidden for a single-topic attempt (`isBreakdownUseful`), since one row restates the ring under a heading promising something new.
- **The review list defaults to the mistakes**, with an All / To review segmented control that only appears when the two options differ. Opening on all 45 questions makes a learner scroll past what they know to find what they do not. Card numbers are the paper's, not the filtered list's — renumbering would make the review disagree with the session just sat — but the entrance stagger uses the *rendered* index, or a filtered list starting at question 41 would stagger past the cap and appear to hesitate before drawing.
- **Review cards show the question's artwork.** A third of the bank is picture questions whose stems carry no information without the picture; the session screen showed it and the review had been dropping it. It is tappable here too, since the review is exactly where a learner has a reason to look closely.
- **A wrong card links into the section that teaches it** ("Study this topic"), on incorrect answers only. The breakdown card above answers a different question — which subject to revise *overall* — and a learner reading one mistake at a time wants the section for the one in front of them. Omitted on a correct answer, where it would be an invitation to go and re-read something already known.

**The screen is a `FlatList` with everything above the review as its header, and that is not cosmetic.** The review list was rendered with `.map()`, so every card mounted at once — 45 of them with images on a full mock, and *several hundred* now that open practice can be finished at all. Virtualising it is what makes finishing an open practice safe. The header is unchanged content, just handed to the list instead of stacked above it, and the entrance stagger uses the same `settled` ref as the Learn section list so cards mounting during a scroll do not animate in under a moving finger.

Two timing details:

- The countdown reads `latest.current` (a ref refreshed **during render**, deliberately — an effect would let a timeout grade the attempt without the last answer).
- Remaining time is derived from a fixed deadline rather than decremented, so it neither drifts across a 30-minute attempt nor pauses while the app is backgrounded. The clock keeps running in the background, which matches a real exam.
- `secondsLeft` lives in its own `ExamClockContext`; on the session context it would re-render every question and choice once per second.

## Design system

`src/theme/tokens.ts` is the only place colour, radius and type are defined. Screens read them through `useTheme()`.

**One palette, and it is binding.** `brand` is a violet ramp (50–950) and every accent, tile, badge, icon and border resolves to a step on it, to a neutral derived from it, or to one of the four `tints` below. The neutrals are deliberately *tinted* toward the brand hue rather than being true greys — `text` is a near-black violet, `shadow` is `brand[950]` — because a neutral grey beside a saturated violet reads as two unrelated systems. `info` **is** the brand: it used to be an unrelated blue sitting a few degrees off the primary in the same screens, which was the single most obvious thing making the palette look accidental.

**The ramp was re-tuned from an electric indigo to a soft violet centred on `#6C5CE7`,** and the step to check before editing it is not 600. That is a small hue shift and a large *chroma* one, and it drags one contrast figure with it: `600` carries white at **4.86:1** (through AA, down from 7.29), and `500` at **3.43:1** is no longer safe for `onPrimary` copy. The light `brand` gradient therefore runs **600→800**, not the old 500→700. The light end of the ramp is still there for tints and washes, where nothing is read on top. If a future accent reaches for `500` as a text background, that is the number to re-check.

**`tints` is a deliberate, bounded widening of the rule above.** Four pastel card fills — lavender, periwinkle, blush, mint — read from the theme like `gradients`. Three properties keep them a system rather than a return to the four-unrelated-hues state the tiles were rescued from:

- **They are card *fills*, never accents, glyph colours or text colours.** `primary` is still the only colour an action is drawn in, so nothing here competes for "this is the thing to press".
- **Each fill carries its own checked `ink`,** because a tinted surface changes the contrast every piece of copy on it is read against — the same fact that makes `Card`'s accent a 3pt rule rather than a tinted background. Every pair clears 4.5:1 in its own scheme. **Always take the ink from the same entry as the fill**; `textMuted` is only checked against `surface`, which is why `Chevron` and the exam chips take an explicit `color`/`ink` prop.
- **The set is closed, and assignment is positional rather than semantic.** `SECTION_TINTS` and `MODE_META` cycle them so adjacent cards in a grid never match; the icon still does the identifying. A fifth tint means editing `tokens.ts` and checking a ratio, which is the friction that stopped the old palette accumulating hues.

Dark tints are not the light ones darkened — at those lightnesses that produces mud — but deep, low-chroma versions of the same hue carrying light ink. Same reversal `gradients` already documents.

**Three tokens keep their conventional hues, and this is not an oversight.** `success`, `danger` and `warning` encode *meaning the app is teaching* rather than decoration — a wrong answer on the result screen, a destructive action, a red dashboard tell-tale. They are tuned to sit with the indigo, not replaced by it.

**Two things are deliberately not monochrome, and must not be made so:**

- **`assets/signs/` — the traffic-sign artwork.** Sign colour is regulatory: a red octagon, a red-bordered triangle and a blue disc *mean* prohibition, warning and obligation, and the bank asks about them. Recolouring these to the brand teaches wrong content and would fail a learner on the real test. They are photographic content, not iconography.
- **`severityTone()` in `(tabs)/learn/[section].tsx`** maps a dashboard tell-tale's `red | amber | green | blue | white` to a text colour. That is the lamp's own colour, which is the entire point of the section — red means stop driving, amber means caution.

The Learn section tiles *were* the real inconsistency and are now monochrome: five tiles ran four hues, two of them sharing `danger`, so the colour was not identifying anything the glyph did not.

**Corner radii were tightened one step** (`sm` 8→6, `md` 12→10, `lg` 16→13, `xl` 24→20). `pill` stays at 999 for genuine pills — a badge at 20 just looks like a mistake.

### The tab bar is a custom component, and that has consequences

`components/ui/floating-tab-bar.tsx`, passed to `<Tabs tabBar={…}>`. A dark pill hovering over the content rather than a bar welded to the bottom edge. It is near-black in **both** schemes (`colors.tabBar`) — the one place the palette stops tracking the theme, and structural rather than stylistic: the bar floats over whatever is scrolling underneath it, so a surface-coloured bar over a surface-coloured card separates from nothing.

Four things follow from replacing the stock bar, and three of them are ways to break something:

- **`tabBarStyle` no longer does anything by itself.** `BottomTabView` renders a custom `tabBar` verbatim; the option is read *inside* the stock `BottomTabBar`. `FloatingTabBar` flattens and honours it explicitly, and that is not cosmetic — the exam session hides the bar because it is otherwise a way out of a running attempt that skips the quit confirmation, leaving it to auto-submit as a failure in the background.
- **Screens must pad for it themselves.** The bar is absolutely positioned, so scenes fill the whole area and `BottomTabBarHeightContext` is never applied as padding. Every screen inside `(tabs)` reads `useTabBarClearance()`; `Screen` deliberately does not do it, because the auth flow, the language picker and the account screen also use `Screen` and would get a hundred points of dead space.
- **The press handler reproduces the stock contract on purpose** — emit `tabPress` first so a listener can `preventDefault`, dispatch with `target: state.key` so a bare name is not resolved against an *ancestor* navigator, and emit `tabLongPress`.
- **The travelling circle negates its offset under RTL.** `translateX` is a physical transform; Yoga's `direction` mirrors the row but never touches a transform, so slot 0 is already on the right and an unnegated offset sends the circle off the end of the bar. Same class of detail as `Chevron` and `Gradient`.

`Texture` also gained an explicit `color`, for this bar specifically: its default mark is `colors.text`, which in light mode is a near-black dot on a near-black bar — a texture that silently does nothing while appearing to work in dark mode.

### Swiping between tabs

The gesture is in `(tabs)/_layout.tsx`; the *decision* is `features/navigation/tabs.ts`, pure and tested, for the same reason `sections.ts` and `entries.ts` sit outside the route directory. `swipeTarget(pathname, translationX, isRTL)` carries three rules, and each fails silently:

- **The direction mirrors.** `translationX` is a physical distance — negative is a finger travelling left in every language — while the tab row is laid out right-to-left in Arabic and Sorani. A version that ignored `isRTL` works perfectly in English and moves *backwards* in the two languages most of the app is written for. Same class of detail as `Chevron`, `Gradient` and the tab bar's travelling circle.
- **It refuses to leave a running attempt.** `isImmersiveRoute` covers `/exam/session` and `/exam/result`, matched as prefixes. Those screens hide the tab bar precisely because any exit skipping the quit confirmation abandons the paper — the provider outlives the screen, keeps counting down and auto-submits it as a failure. A slightly diagonal finger on a long question is exactly such an exit, and one the learner did not choose. This is the same rule `mayNavigateFrom` enforces for a tapped notification, arrived at from the other side.
- **Ends return null rather than clamping.** Re-navigating to the tab already showing resets the stack inside it — swiping outward on Settings would throw away the account screen underneath.

`tabIndexFor` prefix-matches so a swipe works from a detail screen too (`/learn/signs` is still Learn), and matches longest-first so a route that is a prefix of another cannot claim it. `TAB_ROUTES` order must match the order `(tabs)/_layout.tsx` declares, since the whole point is that it moves along the row the reader can see.

### Gradients, texture and elevation

Three additions to the token layer, all resolved through `useTheme()` rather than imported:

- **`gradients`** (`theme/tokens.ts`) — every stop is a step on `brand` or an existing semantic token, so the gradient system is the same palette seen at an angle. Read them from the theme: **the dark ramp is not the light one darkened.** `brand` carries `onPrimary` copy along its whole length, and in dark mode `onPrimary` is near-black, so the dark gradient is read from the *light* end (300→400). Mirroring the light theme's 500→700 would put near-black text on a mid indigo at about 2.7:1.

  **The `…Wash` fade stops are background-at-zero-alpha (`#F7F8FC00`), never `transparent`.** `transparent` is `#00000000`, so a gradient interpolating toward it takes the colour channels toward black as well as the alpha — on Android that renders a visible grey bruise through the fade. The same rule is why `Choice` in the exam runner animates a solid layer's *opacity* instead of interpolating a colour to `transparent`.

- **`Texture`** (`components/ui/texture.tsx`) — an SVG `Pattern` at 5–7% opacity, on by default in `Screen` and rendered *over* the wash (the wash is near-opaque at the top, which is the part of the screen most worth giving a surface to). It exists because a large area of one exact colour reads as absence rather than as material.

  **The screen default is `grain`, not `dots`, and the difference is the point.** `dots` is a single mark centred in an 18pt cell — a halftone, and the eye finds the rows in one even at 7%, which is the one thing a background finish must not let you do: a pattern you can name has stopped being surface and become decoration. `grain` is twelve marks at four radii on a jittered lattice in a 48pt tile, so it has the same coverage with no line to find. The marks are written out rather than generated from a seeded random, so what ships is what was looked at. `dots` stays, and is what the tab bar asks for by name: it is a small busy surface where an irregular field reads as dirt rather than as texture.

  Three constraints: the pattern `id` is derived from `useId()` because two textures mount at once (screen plus tab bar) and a hardcoded id collides silently; **no fragments inside `Pattern`** — `react-native-svg` maps children onto native nodes, a fragment is not one, and nesting one is a reliable way to have children dropped on a single platform (the `grid` variant is one `Path` with two subpaths for exactly that reason, and `grain` maps to an array, which is not a fragment and is fine); and it is **memoised**, because it sits inside `Screen` and was re-reconciling an SVG surface with its own `Defs` on every render of everything above it, to produce the identical tree.

- **`bloom`** — ambient light behind *every* screen, unconditional, drawn under the opt-in wash. It is not a second wash and could not be one: a wash is a statement that this screen opens something, which is why it is opt-in and why putting one everywhere would turn it into wallpaper. The bloom is a fraction of that strength with no edge to notice, and it exists so a screen has a light source rather than being lit from nowhere. The detail screens — `learn/[section]`, `settings/account` — carry no wash at all and were the flattest surfaces in the app before it. It runs to 62% of the screen rather than the wash's 300pt precisely so it has no edge to draw.

- **A `Card`'s finish is a `sheen` gradient, not a `Texture`.** This was a per-card SVG surface carrying its own `Defs` and `Pattern`, and one screen is a dozen of them — eight on settings, seven tiles on the Learn home, plus the screen's own — each mounted and discarded by whatever list the card is in. A `LinearGradient` is one native view and says the more accurate thing anyway: a raised card is not paper with grain in it, it is a plane catching the light. The screen behind it keeps the grain, so the two surfaces are still told apart by their finish, which is what the old `intensity` below 1 was doing.

  **Both `sheen` stops are one colour at two alphas, and it has to stay translucent.** Same-colour-two-alphas is the `…Wash` rule again — a stop interpolating toward `transparent` drags its colour channels to black and Android renders a grey bruise through the fade. Translucency is a second, separate requirement: the Learn grid replaces `Card`'s fill with a `tints` entry, and an opaque `surface → surfaceAlt` sheen would paint the tint out. The two schemes run in *opposite* directions because the light is always above — light mode shades the foot of the card with the shadow neutral, dark mode lifts its head with white, because a shadow on a near-black card is invisible. `texture={false}` still turns it off for a virtualised list row.

- **`elevation` now has a level 3**, indexed by a table rather than nested ternaries. Only `Button`'s primary variant uses level 2+; an elevated secondary is a second thing claiming to be the answer.

**Resolved styles are cached by value, in three places now: `elevation`, `typographyFor`, and `Text`'s colour/alignment triple.** The allocation is the smaller half of why. React Native diffs styles by reference first, so handing it a fresh object for an unchanged value re-flattens and re-sends the whole style — and `Text` is the most instantiated component in the app by a wide margin, six to a Learn card with a dozen cards mounted. Every one of these key spaces is small and closed (four elevations, one scale per script, nine tones times two alignments times two directions), which is the property that makes a plain unbounded `Map` the right structure rather than a leak.

### Motion

`lib/motion.ts` is to animation what `tokens.ts` is to colour: durations, easings and springs live in one place, because a screen that picks its own 400ms while its neighbour picks 250 reads as two apps and the difference is invisible in a diff.

**`useMotion()` is the accessor, and everything it returns is reduce-motion aware.** The rule is *suppress the movement, keep the information*: `entrance()` returns `undefined` when motion is reduced (Reanimated reads that as "no entering animation", so the item mounts in its final position rather than staying invisible), and `ms()` collapses to 0 so a `withTiming` still lands on its target without the call site branching. It is memoised on `reduced` — `renderItem` on the 111-row Learn list closes over it, and a fresh object per render gives `FlatList` a new `renderItem` identity, which is precisely the signal it uses to re-render every mounted cell.

Two things that bite on device rather than at compile time:

- **Resolve `motion.ms(...)` and `motion.reduced` on the JS side before a worklet closes over them.** The body of `useDerivedValue`/`useAnimatedStyle` runs on the UI thread; calling `motion.ms()` inside one means shipping a closure over the whole `Motion` object across the bridge. It typechecks and then fails at runtime, on device only. Every call site here captures plain numbers and booleans.

- **Never pass a function as an *argument* to `runOnJS`.** Only the callable in the `runOnJS(fn)` position survives the hop; the arguments are serialised, and a function among them arrives on the JS thread as a plain object — `TypeError: go is not a function (it is Object)`, thrown at the end of every gesture. This typechecks perfectly, because the types describe the call and not the serialisation. The fix is always the same shape: close over everything the handler needs and send only plain values across. The tab-swipe gesture in `(tabs)/_layout.tsx` sends one number, and it is the only `runOnJS` in the project — `grep -rn "runOnJS" src` if that changes.
- **`STAGGER_MS` is capped at `MAX_STAGGER_MS`.** `index * 55ms` over 111 cards puts the last one a minute out. The Learn section list also only animates the first `FIRST_SCREEN` rows: past that the list is virtualised, so an entering animation fires when a cell mounts *during a scroll*, and rows sliding in under a moving finger read as the list struggling rather than as polish.

**Three screen transitions, each chosen for what it claims about the destination.** The root stack **cross-fades**: its children (the language picker, the auth flow, the tabs) replace one another rather than stacking, so a side push claims a "back" that does not exist. The tab navigator uses **`shift`**, collapsed to `none` under reduced motion — it is a sliding scene transition, exactly the category the OS setting exists to suppress, and nothing is lost by removing it because the destination is identical either way. The exam session and result rise from the **bottom**, which is the platform's idiom for a mode you have to finish rather than a page you can wander out of, and which matches what those screens do (no back button, no gesture, no tab bar). The section stacks keep their mirrored `slide_from_left`/`slide_from_right`; the other three have no horizontal component and so need no mirroring.

**One looping animation exists in the whole app** — the exam clock's beat under the last thirty seconds. It earns the exception because it is bounded, stops on its own, and signals something genuinely urgent. Nothing else loops; an icon that pulses forever is motion the user cannot stop and did not ask for.

### Animated icons

`components/icons/` draws the section, tab, exam-format and settings-group icons as SVG rather than taking them from Ionicons, so each one can animate a *part* rather than the whole.

The four files split by *how* they are driven, not by subject: `section-icons.tsx` and `exam-icons.tsx` play once on mount and on press (`useIconPlayback`), `tab-icons.tsx` tracks focus in both directions (`useFocusDrive`), and `settings-icons.tsx` plays once as its card lands. **The line on what gets drawn is whether it labels or decorates** — one animated icon per card heading, and the small inline glyphs (a tick on a selected option, a chevron, a flame on a streak pill) stay as Ionicons. Animating a 13pt glyph inside a chip does not read as alive, it reads as the screen twitching, and there are a dozen of them on the settings screen. `speedometer-outline` is a picture of a speedometer; a speedometer's meaning is a needle moving. The five Learn sections perform their own idea: the warning triangle draws itself then the mark lands, a vehicle travels the slip road and merges, the clauses write themselves in order, the needle sweeps to 85% and settles back to 65% (the ignition self-test — a needle that eases straight to its resting value looks like a slider), the prohibition bar strikes through.

Four rules everything in that directory is built to:

- **`progress === 1` is the resting state, not the end of a flourish.** This is what makes reduced motion a one-line answer — start at 1 and never move — and it is the classic bug when it is backwards: the icon plays beautifully and then rests half-drawn.
- **Only numeric SVG props are animated** (`strokeDashoffset`, `opacity`, `r`, endpoint coordinates). No `d` strings built in worklets, no animated transforms on `G`; both are markedly more fragile across platforms than plain numbers. Where a whole glyph must rotate — the settings cog — it is a `View` transform, which pivots on its own centre for free.
- **Section icons play once** (`useIconPlayback`, replayed on a press counter, not a boolean — a boolean can only change once, and tapping a card twice has to play twice). **Tab icons track focus in both directions** via `useFocusDrive`, because a tab is a state, not an event, and tapping away has to reverse rather than replay.
- **Path lengths are written out, not measured.** `getTotalLength` has no counterpart in `react-native-svg`.

`RulesIcon` flips the anchor end of its dash offset in RTL, so the clauses write themselves right-to-left in Arabic and Sorani — the same class of detail as `Chevron`. `Gradient` mirrors its axis for the same reason (`vertical` is exempt: it has no horizontal component, and flipping it would be a no-op that only looked like a decision).

### Three graphics mistakes worth not repeating

All three were made and then fixed here, and all three look plausible in code:

- **A glow is not a wide stroke.** SVG strokes have hard edges, so a "halo" drawn as a thicker stroke at low opacity renders as a second concentric band with two crisp boundaries — visibly a ring someone forgot to delete. A real glow needs opacity falling off with distance, which is a `RadialGradient` whose stops share one colour and vary only in `stopOpacity` (so nothing interpolates toward black, and the palette rule still holds). `ScoreRing`'s canvas is also larger than its ring, so the falloff has somewhere to go: a glow clipped by its own viewport shows a hard circular edge exactly where there should be nothing.
- **A break in a continuous stroke reads as damage, not as an annotation.** The pass mark was first drawn *across* the ring in the surface colour, on the reasoning that a gap stays visible whether the arc has covered it or not. It does, and it also looks like a scratch. It is now a short tick set outside the track in a muted neutral.

- **`preserveAspectRatio="none"` distorts geometry, not just strokes.** `Sparkline` used to lay out in a fixed 100-unit viewBox stretched to the card, which needs no measurement pass and is wrong for anything round: on a 340pt card the horizontal scale is ~3.4x against a vertical 1x, so `r={2.5}` drew the newest attempt as an 8.5×2.5pt ellipse. `vectorEffect="non-scaling-stroke"` does not save it — that exempts the stroke width and nothing else. It now measures itself once with `onLayout` and computes the geometry in real points, which also lets the pass-mark label be positioned against the same scale the plot uses rather than against a hand-kept second copy of it.

Related: `ScoreRing`'s arc gradient runs 0.75→1, not 0.55→1. A wide range makes the start of the arc look faded rather than lit, which is how a gradient ends up reading as a rendering error.

### The trend line says two things, in two channels

`Sparkline` on the exam home. The **line** is the brand accent and carries the shape of the run; the **dots** are `success`/`danger` per attempt and carry each one's verdict against the pass mark. Colouring the whole line green or red said the same thing twice at lower resolution — a run that fell from 90 to 75 is a decline that still passed every time, and one red line cannot say that. Per-point dots are also what stop the reader having to measure each point against the dashed rule by eye.

Two constraints carried over unchanged, and both still matter: **the y-axis is pinned to 0–100** rather than scaled to the data, because an auto-scaled axis renders 61, 62, 63 as a dramatic climb and 88, 90, 89 as noise; and **modes are never mixed**, because a 15-question warm-up beside a 45-question mock is two different tests and a line joining them asserts a trend that does not exist. The card's headline delta is measured across the whole plotted window rather than against the single previous attempt — it is answering "am I getting better", and one bad morning in the middle of a rising run should not turn the card red.

**Springs are for things being moved, not things being presented.** The artwork viewer's zoom is a plain timed ease deliberately — a spring overshoots and settles back, and on an image the user opened in order to look at it closely, that reads as a wobble. `spring.press` on `PressableScale` is the opposite case and is correct.

### The headline serif

`display`, `title` and `heading` are a serif; body variants stay on the system sans, because a serif at 13pt in a hundred-row study list costs legibility rather than buying luxury.

**There are two families because there has to be.** Playfair Display carries no Arabic glyphs, and `heading` is not decorative here — sign titles in the Learn list render at it. One Latin face set globally would drop every Arabic and Sorani headline to tofu on Android and a silent substitution on iOS. `NotoNaskhArabic` is the counterpart and covers the extended Perso-Arabic letters Sorani needs. `arabicFace` is typed as a total `Record`, so adding a Latin display face without an Arabic equivalent is a compile error.

Three constraints on edits:

- **Weight is baked into the family name, so these variants set `fontWeight: 'normal'`.** Naming `PlayfairDisplay_700Bold` *and* a numeric weight makes Android hunt for a bold cut of a family that is already the bold cut, and it either synthesises a smeared double-bold or falls back to the default face.
- **The Latin scale gained a leading floor of 1.34.** Same clamp bug as the Arabic one, arriving from the Latin side for the first time: Playfair declares a **1.333em** line box against the system sans's ~1.2, so the old numbers (`display` 1.19, `title` 1.25, `heading` 1.32) would have clipped every English headline the moment the serif was switched on. The Arabic 1.75 floor did **not** move — Noto Naskh declares **1.703em**, which it already clears. Both figures were read out of the shipped `.ttf` (`head.unitsPerEm`, `hhea` ascent/descent/gap), not off a specimen page; re-read them if either family is swapped.
- **Import fonts from the per-weight entry point** (`@expo-google-fonts/playfair-display/700Bold`), never the package root. Each root `index.js` re-exports every cut it ships, and a `require` of a `.ttf` is an asset Metro resolves eagerly — importing from the root bundled all sixteen files (~2.9 MB) to use four (~788 kB).

Loading is gated in `src/app/_layout.tsx` alongside `preferences.ready`, so nothing paints in the sans and reflows a frame later. **`fontsError` is part of the gate, not just logged:** `useFonts` leaves `loaded` false forever when a file fails to decode, so gating on `loaded` alone trades a wrong-looking headline for a permanently blank app. It fails open to the system font.

`typography.test.ts` pins all of this and is mutation-checked: making the Arabic scale pass the Latin face through fails the tofu guard, and reverting the Latin leading fails the line-box floor.

## i18n and RTL

`src/i18n/locales/en.ts` is the **typed source of truth**. `ar.ts` and `ckb.ts` are declared as `TranslationShape`, so a missing or misspelled key is a compile error rather than a silent runtime fallback. Add keys to `en.ts` first.

Arabic and Sorani are both RTL, and **the app carries direction itself rather than delegating it to `I18nManager`**. `applyDirection()` only *normalises the native flag away* — `allowRTL(false)`, plus a one-time `forceRTL(false)` on a device an older build had already flipped — and returns nothing.

That is a deliberate reversal. Direction used to ride on `I18nManager.forceRTL`, which is process-wide and only takes effect on a full relaunch, so Settings showed a "restart the app" notice. **Do not reinstate `forceRTL`** — the notice it justified is gone, so the app would silently draw one direction while the native flag claimed another. `typography.test.ts` pins this and fails if `forceRTL(true)` returns.

### Four properties, one resolver

`directionFor(language)` in `src/i18n/index.ts` returns all four, and the theme spreads it. They are separate jobs decided by one fact, and the failure mode is never a total absence of mirroring — it is **one of them lagging**, which is the "almost mirrored" state that reads as broken where being wholly unmirrored just reads as unfinished.

| Property | What it moves | Where it is applied |
| --- | --- | --- |
| `direction` | the boxes — every `flexDirection: 'row'`, `flex-start`, `marginStart`, `paddingStart` | once, on the root `View` in `app/_layout.tsx`; Yoga inherits it down the tree |
| `paragraphAlign` | the side a `<Text>` paragraph sits on inside its box | `Text` only |
| `inputAlign` | the same, for a `<TextInput>` | `Field`, the Learn search box |
| `writingDirection` | the *order* of a mixed run — Latin words, numerals, `%` inside an Arabic line | all three |

**`paragraphAlign` is `'left'` in Arabic and Sorani, and that is the fix rather than the bug.** React Native treats `textAlign: 'left' | 'right'` on a `<Text>` as **logical**: it resolves them against the node's inherited Yoga direction and swaps the pair when that direction is RTL. Both platforms, same shape — iOS in `RCTAttributedTextUtils.mm` (`if layoutDirection == RightToLeft` → `Right`↔`Left`), Android in `ReactBaseTextShadowNode.getTextAlign()` (guarded on `YogaDirection.RTL`, swapping `Gravity.RIGHT`/`LEFT`). So the app's two halves were cancelling out: the root's `direction: 'rtl'` mirrored every box *and* turned an explicit `textAlign: 'right'` into a real left edge. **Every paragraph in the app rendered hard against the left of a correctly mirrored screen**, which is how this reached a user. `'left'` means *start* in both directions, so it is a constant — do not "correct" it to track the language.

**`inputAlign` is physical and must stay a separate field.** `layoutDirection` is attached to text attributes in exactly one place in React Native — `ParagraphShadowNode`, which backs `<Text>` — and in none of the TextInput shadow nodes, so the swap never runs for an input. One value serving both is precisely what left the Learn search box correctly on the right while every paragraph beside it ran to the left. `direction.test.ts` pins both halves and is mutation-checked: making `paragraphAlign` track the language fails 2, and collapsing `inputAlign` onto it fails 2.

The practical consequence for new code: **never set `textAlign` on a `<Text>` by hand.** Use the `Text` component, or read `paragraphAlign` from the theme. A literal `textAlign: 'right'` in `src/` is a bug that will look correct to whoever wrote it and render on the wrong side.

`direction` is Yoga's own property, so the whole tree mirrors on the frame the language changes with no relaunch and no native flag. `src/i18n/direction.test.ts` pins them staying in step and is mutation-checked: desyncing `writingDirection` from `direction` fails it.

**Consequence for new code: never write a physical edge.** Use `start`/`end`, `marginStart`/`paddingEnd`, `borderStartWidth`. A `left:`/`marginRight:` anywhere in `src/` is a bug — it will not mirror, and it will look correct to whoever wrote it. `grep -nE "(margin|padding|border)(Left|Right)|^\s*(left|right):" src` should only ever match a genuinely symmetric pair (`left: 0, right: 0` on a full-bleed layer).

### The two places direction does *not* inherit

Both are documented at their call sites, and both are the reason the app once looked "almost right" in Arabic:

- **`Modal`.** React Native hosts a modal's children on a **separate root**, so the subtree starts from the platform default rather than from anything above it in the React tree. `ArtworkViewer` re-applies `direction` itself. Any future modal must too.
- **A native stack header.** A `UINavigationBar` / Android `Toolbar` is laid out by the platform, and the platform reads `I18nManager.isRTL` — which this app keeps false on purpose. So the header kept its back button on the left and its title left-aligned over a screen that had mirrored, and a detail screen slid in from the left *toward* the back button. **The stacks now render `ScreenHeader`, a JS header, through `header` in `useStackScreenOptions`.** It is an ordinary row in the same tree, so it mirrors with everything else. `NativeStackView` disables the native header whenever `header` is set, so there is no second bar — but it applies **no top inset** to a custom one, which is why `ScreenHeader` reads `useSafeAreaInsets()` and why the screens under it pass `edges={[]}` to `Screen`. Claiming the top edge in both places double-counts the status bar.

### Anything that *points* has to be chosen from the language

Mirroring the layout moves an icon to the correct edge; it does not turn the picture round. Four things resolve their own direction rather than being flipped by Yoga:

- **`Chevron`** takes `points="forward" | "back"` — reading-order words, not compass ones. The glyph is `chevron-forward` exactly when `points === 'forward'` disagrees with `isRTL`, which is the whole rule.
- **`Gradient`** mirrors its axis, so emphasis stays under the first word (`vertical` is exempt — no horizontal component to mirror).
- **The stack push animation** is named explicitly (`slide_from_left` in RTL), because the native stack would otherwise take the side from `I18nManager`.
- **`Sparkline`** runs its time axis right-to-left, and `RulesIcon` flips the anchor end of its dash offset.

Not everything that could mirror should: `severityTone`, the sign artwork, and `PriorityIcon`'s slip road merging from the right are all facts about the road rather than about the reader.

### Search has to fold the script, or it does not work in Arabic

`i18n/fold.ts`. The Learn tab's search box matched raw lower-cased text, which is correct in English and quietly broken in the two languages most of the app is written for. Three causes, none visible to whoever wrote the note:

- **Harakat.** The study notes carry short vowels where they help a learner read — `الدوّار`, `تقريبًا`, `كلًّا` — and nobody types them into a search box. `الدوار` and `الدوّار` are one word with one invisible mark between two letters, and `String.includes` says no.
- **Letters with more than one spelling.** `أ إ آ ا` are one letter for the purpose of finding a word, as are `ة`/`ه` and `ى`/`ي`. Someone typing `اشاره` never finds `إشارة`, and has no way to learn why.
- **Digits.** The notes print `٦٠ كم/س` and the bank prints `60`, so a learner reading one and searching the other found nothing.

**Fold both sides or it does nothing** — folding only the index moves the mismatch rather than removing it. `buildGroups` folds `Entry.search` once at build time and the screen folds the query on each keystroke, which works because `foldForSearch` is idempotent.

**The Sorani half is the one that keeps this from going too far.** `ڕ ڵ ۆ ێ ژ چ گ پ` are distinct letters in Kurdish, not variants of an Arabic one, and folding them would merge words a Kurdish reader knows are different. Over-folding is how a normaliser gets reverted rather than tuned, so `fold.test.ts` asserts it as hard as the harakat cases.

### Enumeration follows the script, not the direction

`features/exam/choice-markers.ts` labels answer options أ ب ج د in Arabic and Sorani and A B C D in English. It was `String.fromCharCode(65 + position)`, which put Latin letters inside an Arabic question card on an otherwise fully localised screen. Keyed by `Script` rather than by language — Sorani is a different language sharing the alphabet — and the `Record` is total, so adding a writing system without markers is a compile error. `choice-markers.test.ts` pins the coupling to `MAX_CHOICES_PER_QUESTION`, which is otherwise invisible: raising the schema bound to five would leave every fifth option labelled `5` in a list of letters.

**Still not mirrored, and knowingly:** `Alert` and `Switch` are OS-drawn and take their direction from the device locale, not from the app. Fixing either means replacing it with a JS component, which has not been worth it.

**Line height is script-dependent, and this is not cosmetic.** An explicit `lineHeight` is a *clamp*: React Native rewrites the font's ascent and descent to fit it (`CustomLineHeightSpan` on Android, the paragraph style on iOS), so a script whose natural box is taller gets **cut off** rather than given room. Latin sits near 1.2x and had slack under the shipped scale; Arabic runs to about 1.75x once harakat stack above the letters, and `body` at 1.5x sliced them. It reached a user as two signs — `sign-flammable-load` (fathatan in `نظرًا`) and `sign-crossroads-ahead` (kasra + shadda in `التخطِّي`) — rendering clipped in Arabic while identical records were fine in English and Kurdish.

`typographyFor(script)` in `theme/tokens.ts` applies a 1.75x **floor**, exposed through `useTheme().typography`. Three things about it:

- **Read it from the theme, never import `typography` directly into a component.** `Button` used to pass `typography.bodyStrong` as a *style override*, which put the Latin line height straight back on top of the resolved one — a way for one component to stay broken while everything else was fixed.
- **`Math.ceil`, not `Math.round`.** `heading` is 19pt and `round(19 * 1.75)` is 33 against a floor of 33.25 — a floor that rounds below itself is not a floor. The test caught this, not review.
- **Sorani is covered too, deliberately.** Same script, same metrics; it escaped only because none of its shipped strings happen to use harakat, which is luck rather than safety.

## Provider order

`src/app/_layout.tsx` nests providers in a required order: `SafeAreaProvider` → `PreferencesProvider` → `AppThemeProvider` → `AuthProvider` → `AvatarProvider` → `GoalProvider`. Theme resolves `light | dark | system` from preferences, so it must sit inside it. `AvatarProvider` reads `user.id` to decide whose picture it may show, so it must sit inside auth. `GoalProvider` sits above the tabs because the exam runner writes to it and the Learn hero reads it — they are in different tabs, and the point of the ring is that it has moved when you come back. Rendering is gated on `preferences.ready` so persisted language/theme apply before first paint.

`src/app/index.tsx` is the routing gate: language picker → auth → tabs. It waits for `auth.ready` before deciding, so a signed-in user is not bounced to sign-in on a cold start.

**`(tabs)/_layout.tsx` re-checks auth, and that duplication is deliberate.** The index gate only runs when the user lands on `/`, which a deep link does not: `ejazty://learn` mounts the tabs navigator directly, so the scheme registered in `app.json` was a way around it. Gating at the group rather than at one route also means a screen added under `(tabs)` later is protected by default instead of by whoever remembers. It waits for `ready` for the same reason index does.

## Notifications

`features/notifications/` schedules **local** reminders — no push server. Slots come from `REMINDER_HOURS` (07:00 · 12:00 · 17:00 · 22:00 — four, exactly five hours apart, with the overnight gap absorbing the rest of the day) with ±25 min jitter, queued three days ahead and topped up on every foreground.

**`features/notifications/schedule.ts` decides *when*, and it is pure.** `planReminders` takes `now`, the slot hours, the horizon, the existing draws and whether today's goal is met, and returns the instants plus the draw record to persist. It was inline in `index.ts` behind four native calls, where none of it could be tested and every one of its mistakes is unobservable: a reminder planned into the past silently never arrives, a dropped draw record lets the next rebuild re-roll a day and repeat a message already delivered, and a suppression rule one day too wide empties the queue for everyone who ever meets a goal. `random` is injected alongside `now` because jitter is the one input a test could not otherwise pin. `schedule.test.ts` is mutation-checked: widening the goal suppression past today fails 1, recording the draw only for surviving slots fails 2.

**Reminders stand down for the rest of the day once the goal is met.** Nagging someone who has already studied is what people turn reminders off over, and off means none at all. Two halves make it work: `planReminders` drops *today's* remaining slots (today only — tomorrow's goal does not exist yet), and `GoalProvider` calls `refreshReminders` on the crossing rather than waiting for the next foreground, because the goal is met *inside* the app and the learner's next move is to close it with the evening's reminders still queued. The provider guards on the day rather than on detecting the crossing, since `record` resolves asynchronously and can land out of order.

**`REMINDER_FREQUENCIES` lets the learner pick 1, 2 or 4 a day**, mapped to slot hours by `REMINDER_SLOT_HOURS` — a total `Record` of subsets of `REMINDER_HOURS`, written out rather than sliced because slicing would silently answer "which hours survive?" with "the earliest", the worst available answer. Four stays the default so turning reminders on behaves as it did before the setting existed. The settings card shows the resulting times, derived from the same constant, so the screen cannot advertise a schedule the scheduler does not keep.

**The Android notification icon is configured, and it must stay that way.** `app.json` passes `icon: "./assets/images/android-icon-monochrome.png"` to the `expo-notifications` plugin. Without it the plugin emits **no** `expo.modules.notifications.default_notification_icon` meta-data (measured: 0 entries via `expo config --type introspect`, against 1 with the prop), and Android falls back to the launcher icon for the small status-bar icon — which since API 21 is drawn as an alpha silhouette. `assets/images/icon.png` is PNG colour type **2, RGB with no alpha at all**, so every pixel is opaque and the silhouette is a solid filled square. The monochrome asset is 92.5% transparent at uniform luminance, i.e. a real silhouette. `color` alone does not help; it only tints whatever shape the icon produces. iOS is unaffected — it uses the app icon properly.

**`channelId` goes on the trigger, never on `content`.** `NotificationContentInput` has no such field; putting one there typechecks *only* because a conditional spread defeats excess-property checking, so it was silently dropped and every Android reminder landed on the fallback channel instead of the localized `study-reminders` one created moments earlier. This was a shipped bug. Check the installed `Notifications.types.d.ts` rather than assuming — the field has moved between versions.

**The queue marker records everything that shapes the queue**, not just the horizon: language, `coversThrough`, frequency, and the day whose slots were suppressed. `refreshReminders` skips a rebuild while the marker still describes what the OS holds, so a field missing from the comparison makes the skip go stale — the frequency picker would appear to do nothing until midnight, and reminders the learner just earned the right not to receive would still arrive.

Four more things that constrain edits:

- **`PreferencesProvider` must import this module statically — never with `await import()`.** A dynamic import is a Metro **async split point**, and Expo Go serves dev bundles with `lazy=true`, so the chunk is not in the bundle the device downloaded: it is fetched over HTTP from the dev server at the instant the user taps. A failed fetch rejects out of `expo/src/async-require/fetchAsync` as `LoadBundleFromServerRequestError`, and since both setters are called as `void`, it lands as an unhandled rejection with a stack pointing into `@babel/runtime` rather than anything the screen can show — changing language and flipping the reminders switch were both broken this way. The split bought nothing regardless: `src/app/_layout.tsx` already imports this module at the top level, so it is in the main bundle either way. These are the only two `import()` call sites the app ever had; verify with `grep -rn "import(" src` and, on the dev bundle, `asyncRequire` and `dependencyMap.paths` should both be **zero**.

- **Every queue rebuild is serialised through one promise chain** (`serialise` in `features/notifications/index.ts`). `scheduleReminders` is cancel-then-schedule with an `await` between the halves, and `refreshReminders` runs both on mount and on every foreground — so two overlapping runs interleave into twenty-four queued reminders (every notification delivered twice) or wipe a rebuild mid-flight. `refreshReminders`, `cancelReminders` and `rescheduleForLanguageChange` all take the lock, and each runs its *decision* inside it, not just the write: `rescheduleForLanguageChange` is the sharp case, because its "is anything pending?" check reads zero during another rebuild's cancel window and would return early, leaving the whole queue in the previous language — the one failure it exists to prevent.
- **Reminder text is baked in at schedule time**, so changing language must cancel and re-queue everything (`rescheduleForLanguageChange`).
- **No message repeats within a calendar day.** A day's four messages are drawn by shuffling the 13-message list and slicing, and the draw is persisted per date so a mid-day reschedule reuses it rather than risking a collision.

**`setRemindersEnabled` returns the effective state, and `PreferencesProvider` must persist *that*, not the requested value.** It returns false when the OS permission prompt was declined. Storing the request instead left the switch saved as ON with nothing scheduled behind it, and because a declined prompt often cannot be re-shown, that survived every restart — the toggle claimed reminders were on forever.

**It must also never reject, which is the same guarantee arrived at from the other side.** A rejection skips the provider's correction *and* its write, so the switch stays showing ON — and the settings screen calls the toggle with `void`, so it escapes unhandled as well. Every native call reachable from there (both permission calls, the cancel, the Android channel write) is restricted or absent in Expo Go, the workflow SDK 54 is pinned to preserve, so this is the ordinary path rather than an exotic one. It fails closed instead: the switch snaps back to OFF, which is truthful and recoverable. `reminders.test.ts` pins all four throwing paths and is mutation-checked — reverting any one of them fails it.

**A tapped reminder opens the tab it advertised, and `features/notifications/routing.ts` is where that decision lives.** Before it, a reminder was a nudge that led nowhere: tapping "Try the Full Mock Exam" brought the app up on whatever screen it had been left on. `REMINDER_DESTINATIONS` is a total `Record`, so a message added without saying where it goes is a compile error rather than a tap that falls through — which matters because the copy makes a specific promise and routing exists to keep it. The destination is attached to the notification at schedule time rather than looked up on arrival, since these sit in the OS queue for up to three days and the tap may be handled by a later build.

Three things constrain edits:

- **`destinationFrom` validates, and it is not being paranoid for its own sake.** The payload arrives from outside the app — a stale queue written by a previous build, and on Android any app may post to a channel — so it is an arbitrary value about to be handed to the router. expo-router throws on an unmatched href. Only the two tab roots are accepted; anything else resolves to null, which means "open the app and change nothing".
- **`mayNavigateFrom` refuses to leave a running attempt.** The session screen has no tab bar precisely because any exit skipping the quit confirmation abandons the attempt — the provider outlives the screen, keeps counting down and auto-submits it as a failure — and a notification is the one such exit the learner did not choose. A 17:00 reminder must not throw away the mock they are twenty questions into.
- **Both arrivals are handled, and the cold-start one is deduped by identifier.** A tap while merely backgrounded fires the listener; a tap that *launches* the app happens before any listener exists and is only recoverable from `getLastNotificationResponseAsync`, which keeps returning the same launch response for the life of the process — so without the guard every remount of the root navigator would yank the reader back to the exam tab.

`routing.test.ts` pins both rules and is mutation-checked: dropping the destination validation fails 1, and making `mayNavigateFrom` always allow fails 2. The listener around them is React wiring with no rule in it; the rules are the half worth testing, and neither is reachable by hand — a stale payload only appears on an upgrade over an already-scheduled queue.

Reminders cannot be verified in Expo Go — `expo-notifications` is restricted there. A development build is required.

## Auth

Supabase, via `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `.env` (gitignored; inlined at build time, so restart the dev server after editing). Both are public by design and are also pinned per profile in `eas.json`, so a build cannot inherit whichever values happened to be in the shell.

**Project settings live in `supabase/config.toml` and are applied with `supabase config push`.** Password policy, secure email change, secure password change, the per-user mail throttle and the rate limits are all pinned there rather than being dashboard state nothing can assert. Two cautions: `config push` sends a **whole configuration, not a patch**, so a key the file omits goes up at the CLI's default — and two stock defaults would break this project (`enable_confirmations = false` disables email confirmation, which `signUp()`'s `needsConfirmation` branch assumes is on; `site_url` defaults to localhost, which sends recovery mail nowhere). Run the first push **without `--yes`** and read the diff.

**`additional_redirect_urls` holds exactly one entry — `ejazty://reset-password` — and an `exp://` line must not be added to it.** It used to carry one so recovery could be tested under Expo Go, and the 2026-08-07 security review removed it: the anon key is extractable, so *anyone* can call `resetPasswordForEmail(victim, { redirectTo: <any allow-listed URL> })` and their client keeps the PKCE `code_verifier` — so whoever answers on that LAN address receives the one-time `?code=` when the victim taps, and exchanges it. PKCE does **not** cover this, because the interceptor is also the initiator. Test recovery on a separate dev project or on a development build instead; `config.toml` and `SECURITY.md` §3 both spell out the options. `site_url` stays a dead `http://localhost:3000` for the same class of reason — a custom scheme there would be a broad hijack surface, and a URL resolving to nothing hands nothing to anybody.

`supabase` is **null when unconfigured** — every caller must handle that, and the app is designed to boot and be explorable without it. A guest path (`continueAsGuest`) exists for that reason. **That latitude is dev-only:** `src/lib/supabase.ts` throws at import time when the credentials are missing and `__DEV__` is false, because a release build that silently lost its backend strands every user in guest mode, writing history to a cache a reinstall erases.

**The session lives in SecureStore, not AsyncStorage.** `src/lib/secure-storage.ts` is the storage adapter passed to `createClient`. The stored value is a long-lived refresh token — with `autoRefreshToken` on it stays usable until an explicit sign-out — so AsyncStorage (unencrypted on both platforms) meant a rooted device, an unencrypted backup or a forensic extraction handed over the account. Three things about that adapter constrain edits:

- **Values are chunked** across `key.0`, `key.1`, … because SecureStore warns past 2048 bytes on Android and a session carrying `user_metadata` can exceed it. Chunk 0's absence is what "no value" means; there is no separate length record to fall out of step.
- **`setItem` deletes before writing.** Without that, a session that shrank leaves a stale trailing chunk that `readChunks` splices onto the end, handing Supabase unparseable JSON — which surfaces as an unexplained sign-out.
- **`getItem` migrates a pre-SecureStore session out of AsyncStorage** and deletes the plaintext copy. Removing that step signs every existing user out on upgrade; removing the delete leaves the readable token on disk and defeats the change.
- **Every chunk is written with `keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY`.** The SecureStore default is `WHEN_UNLOCKED`, which is *included in encrypted iCloud and iTunes backups* and restores onto other hardware — so the same refresh token that AsyncStorage exposed to a filesystem read would still have been recoverable from a compromised backup. `..._THIS_DEVICE_ONLY` keeps the identical unlock semantics (background token refresh is unaffected) and excludes the item from backups. The accepted trade: restoring onto a new iPhone arrives signed out. iOS only — on Android the value is encrypted with a Keystore key that never leaves the device.

SecureStore has no web implementation. Rather than let Supabase fall back to localStorage — where the refresh token is readable by any script on the page and stays valid until an explicit sign-out — **web runs unpersisted** (`persistSession: !isWeb`) and the user re-authenticates on reload. Web is `npm run web`, a development convenience: EAS builds iOS and Android only and there is no web deploy config in the repo. If web ever ships, that needs a real answer (a server exchanging the session for an httpOnly cookie), not a silent return to the default.

### Password recovery

`resetPasswordForEmail` → deep link → `(auth)/reset-password`. `redirectTo` is built with `Linking.createURL`, so it resolves to `exp://…/--/reset-password` under Expo Go and `ejazty://reset-password` standalone. **Only the standalone form is allow-listed, deliberately** — see the note on `additional_redirect_urls` above for why an `exp://` entry is an account-takeover path rather than a convenience. The consequence to expect: **recovery cannot be tested under Expo Go**, because the mail falls back to `site_url` and never reaches the app. That is the intended default; use a separate dev project or a development build.

`features/auth/recovery.ts` parses the link and is deliberately pure — no Supabase import, no navigation — because the link arrives in three shapes depending on a dashboard setting nobody reads that file next to: `?code=` (PKCE), `#access_token=&refresh_token=` (implicit), or `#error_code=`. **The error shape is checked first**: an expired link can still carry a `code`, and taking it drops the user on a form that cannot save. **`flowType` is pinned to `'pkce'`, and must stay there.** The supabase-js default is `implicit`, which delivers a recovery session as `#access_token=&refresh_token=` in the deep-link URL itself. `ejazty://` is a custom scheme and Android does not enforce uniqueness for those, so any installed app may register the same one — under the implicit flow, a hostile app that wins the race reads a live, long-lived session straight out of the link and owns the account. Under PKCE the link carries only `?code=`, which is inert without the `code_verifier` held in this install's SecureStore. The parser accepts both shapes, so this costs no client code; it does move the **sign-up confirmation** link to `?code=` as well, which is why both email flows get retested when this line changes. The real fix for scheme hijacking is verified App Links / Universal Links once a domain exists — PKCE is what makes interception harmless until then.

**Parsing a shape and acting on it are separate decisions, and `redeemableLink()` is where the second one lives.** The parser still reports the implicit `tokens` shape, because the flow type is a dashboard setting and a parser that silently ignored a shape it might one day receive would be the harder bug. But the app refuses to *act* on it: since a custom scheme is not exclusive, any installed app or web page can hand this screen a URL carrying a ready-made session, and `setSession`-ing it is session fixation — the victim is signed into the **attacker's** account without noticing, and everything they study afterwards syncs there. (What limits the damage is the `ownerId` check in `attempts.ts`, which drops a cache owned by a different account rather than pushing it, so the victim's existing history does not follow them across.) `redeemableLink` converts the shape into `flow_state_not_found`, which already maps to "request a fresh link". If the project ever moves back to the implicit flow deliberately, that function is the one line to change — and `recovery.test.ts` pins the rejection, because the provider is a React context and cannot be reached from the test suite.

`requestPasswordReset` resolves even for an address with no account. Supabase returns success either way, and reporting "no account" would make that screen an email-enumeration oracle — hence the "if an account exists" wording.

`signUp()` returns `{ needsConfirmation }`, derived from whether Supabase handed back a session. Callers **must** branch on it: with email confirmation on there is no session and the screen shows a "check your email" notice; with it off, sign-up signs the user straight in and the screen has to route to the tabs. Showing the notice unconditionally left an account holder signed in but stranded on the sign-up screen.

**This project runs with email confirmation OFF** (`auth.email.enable_confirmations = false` in `supabase/config.toml`, a product decision taken on 2026-08-04). So the live path is the second one — sign-up returns a session and routes straight to `/learn`, and the "check your email" notice is currently unreachable. Keep the branch anyway: it is one config key from being live again, and the earlier version of this note asserted the opposite was true, which is how a screen ends up stranding people. The accepted trade is that an address is never proven to belong to whoever registered it — someone can squat an address they do not own, though recovery mail still goes to the real owner, so it gains them nothing further.

Credential rules live in `features/auth/validation.ts` (`EMAIL_PATTERN`, `MIN_PASSWORD_LENGTH`, `MAX_NAME_LENGTH`), shared by sign-in, sign-up and the account screen. A password minimum that differed between sign-up and "change password" would let someone set a password they could not have registered with.

**`MIN_PASSWORD_LENGTH = 8` is pinned server-side in `supabase/config.toml`** (`auth.minimum_password_length`). It used to be advisory: GoTrue's own default is 6, and the anon key ships in the bundle, so anything posting straight to `/auth/v1/signup` could register a password this app would have refused. Raising the constant now means raising the config key in the same change. `weak_password` is already mapped to a translated message.

**Guessability is checked in `features/auth/password-strength.ts`, not on the server.** Supabase's leaked-password check (HIBP) is a **Pro-plan feature**, so it is unavailable on this project; `passwordProblemKey()` is what stands in its place, and it is what NIST SP 800-63B §5.1.1.2 actually asks for — a comparison against known-common values, which the standard explicitly allows to be a curated list rather than a full breach corpus.

Being client-side is acceptable here in a way it was not for `reauth.ts`, and the reason is worth keeping straight: credential stuffing works because a **real user** picked a breached password, and a real user picks it through this app. Someone bypassing the app to POST a weak password at GoTrue only weakens their own throwaway account. Turn the Supabase toggle on anyway the day the project moves to Pro — the two compose, and the server one cannot be bypassed at all.

Three things constrain edits:

- **It runs on sign-up, password change and reset — never on sign-in.** Existing users may hold a password these rules would reject, and refusing their sign-in would lock them out of their own accounts to protect them.
- **`COMMON_PASSWORD_BASES` holds bare *bases*, not whole passwords.** The checker strips padding and undoes leet substitutions first, so `password` also covers `password1`, `P@ssw0rd123!` and `passw0rd2024`. Adding `password1` to the list does nothing. Entries with *internal* digits (`1qaz2wsx`, a keyboard column walk) are the exception and must be listed literally.
- **`BASE_DOMINANCE = 0.5` is the line between a useful rule and one that gets deleted.** A plain "contains a common word" test rejects `correct horse battery staple` because `horse` is listed. Requiring the base to be at least half the string keeps that passphrase while still rejecting `mypasswordhere`. The `accepts passwords a real person would reasonably choose` block in the tests exists solely to hold that line — over-strictness is the failure mode that gets the whole check reverted.

The region-specific entries (transliterated Arabic and Kurdish names, Iraqi place names, `habibi`, `inshallah`, `peshmerga`) are the ones a generic English list would never have and are the likeliest to matter for this audience. Same for the app's own vocabulary, which NIST calls out by name as "context-specific words".

**`MAX_NAME_LENGTH = 80` is coupled to SQL and is not a cosmetic limit.** `handle_new_user` copies `user_metadata.full_name` into `profiles.display_name` *inside the `auth.users` insert*, and that column has an 80-character CHECK. Before this was bounded, a longer name raised `check_violation`, rolled the whole registration back, and surfaced as the generic "something went wrong" — unfixable by retrying, so anyone with a long name simply could not register. Three sites now agree: the constant, the CHECK in `20260803170000`, and the `left(…, 80)` truncation added to the trigger in `20260803180000` so no other client can trip it either. Raising one means raising all three.

### Biometric app lock

`features/auth/biometrics.ts` plus `lock-gate.tsx`. **It is a lock over a live session, not a way to sign in** — Supabase already holds a refresh token and refreshes it automatically, so there is no credential a fingerprint could stand in for, and the version that stored the password behind biometrics would be strictly worse than the session that already exists. It guards the exam history and the profile picture on a borrowed phone, which nothing else does.

Three rules, each a way to lock someone out of their own app, all pinned by `biometrics.test.ts` (12 tests):

- **Enabling proves the prompt works first.** Persisting the preference and *then* discovering nothing is enrolled is how a user meets a lock screen their face cannot open. Turning it **off** needs the prompt too, or whoever is holding the unlocked phone simply switches it off.
- **It never rejects**, and persists the *effective* state — the same contract `setRemindersEnabled` documents, arrived at from the same failure. A switch saved ON with nothing behind it claims a protection that does not exist.
- **A lock must have a way out.** The lock screen always offers sign-out, because biometrics stop working — a cut finger, an OS update that clears enrolment — and without it this is a way to permanently lose an account from the device holding it. `signOut` and `deleteAccount` both call `clearLock()`: enrolment is per *device*, so a lock left set would meet the next account on this phone with a prompt they can pass.

The gate is a sibling of the navigator rather than a route, because a route can be navigated past and this has to hold a deep link or a reminder tap. It re-locks only on a real `background → active` round trip; iOS emits `inactive` for the notification shade and the app switcher, and locking on those means a prompt for glancing at a notification.

`app.json` note: **`expo-secure-store` and `expo-local-authentication` both write `NSFaceIDUsageDescription` through `createPermissionsPlugin`, where `false` removes the key.** Whichever runs last wins, so secure-store's old `faceIDPermission: false` would silently delete the string local-authentication needs. Both now carry the same written purpose string — never the plugin's boilerplate, per the store-submission note above.

### Apple and Google sign-in

`features/auth/oauth.ts`. Two mechanisms on purpose: **Apple on iOS is native** (`expo-apple-authentication` → `signInWithIdToken`), because the HIG requires the supplied button and review checks for it; **Google is the browser flow** (`signInWithOAuth` + `openAuthSessionAsync`), which needs no native SDK and keeps the client credentials server-side. Apple's name arrives **only on the first authorisation**, so it is captured then or never.

**`ejazty://auth/callback` is allow-listed, and that does not reopen SECURITY.md §3.** The distinction is who initiates. Recovery is dangerous because the *attacker* can initiate — holding the anon key, they call `resetPasswordForEmail` with an allow-listed `redirectTo` while keeping the PKCE `code_verifier`, so PKCE cannot help. An OAuth sign-in starts in this install and the verifier is held here, so an intercepted `?code=` is inert. **That argument rests entirely on `flowType: 'pkce'` staying pinned.** The `exp://` prohibition is unchanged and applies here too — an allow-listed entry is allow-listed for every flow, including recovery — so OAuth needs a development build, the same as recovery.

Both providers are `enabled = false` in `config.toml` until credentials exist; they need a paid Apple Developer account and a Google Cloud OAuth client, and the secrets read from the environment rather than the file. `codeFromRedirect` lives in `oauth-redirect.ts`, apart from anything importing Supabase, for the same reason `recovery.ts` is pure — otherwise the one testable rule in the flow is unreachable behind four layers of mocks. It checks for an `error` *before* taking a `code`, because a provider can return both and the error is the one that is true.

### CAPTCHA

`features/auth/captcha.ts` is the seam where a bot-protection provider plugs in. All four unauthenticated GoTrue call sites already request a token — `signIn`, `signUp`, `requestPasswordReset`, and **the re-auth inside `updatePassword`**, which is easy to miss because it looks like an authenticated operation but posts to the same `/token?grant_type=password` endpoint as sign-in.

No provider is registered, so `captchaTokenFor` resolves to `undefined` and nothing is attached. Registering one is a single call at start-up; see `supabase/SECURITY.md` §4. The reason it stops there rather than shipping a widget: every CAPTCHA component is a **native module**, which needs a development build and **will not run in Expo Go** — the workflow SDK 54 is pinned to preserve.

**The seam fails open deliberately.** GoTrue is the authority on whether a tokenless request is acceptable; a client that blocked sign-in locally when the widget failed would lock users out of a correctly configured project.

### Account management

`(tabs)/settings/` is a stack: `index` is the settings screen, `account` manages the account. Each section on the account screen owns its own busy/error/notice state — a single shared banner meant saving your name wiped the email section's "check your inbox" notice.

- **That gate assumes the account *has* a password, and `features/auth/identities.ts` is what handles the case where it does not.** An account created with Apple or Google has no `encrypted_password`, so `signInWithPassword` fails for every value the user could type — and fails as `invalid_credentials`, indistinguishable from a typo. All three operations below are gated behind it, so such a user met three forms that could not succeed, with no explanation and **no route to deleting their own account at all**. That is a compliance problem rather than an inconvenience, in a project that went to the trouble of writing `delete_own_account` by hand specifically to avoid shipping a service-role key. The server half agreed independently: the `amr` check inside that function looks for `method = 'password'`, which an OAuth session never carries, so deletion fell through to the weaker `iat` branch and succeeded or failed depending on when the token last refreshed.

  **It is currently latent, which is the reason it was worth closing now.** Both providers are `enabled = false` in `config.toml`, so no such account can exist — but `<SocialSignIn>` is rendered on both auth screens gated only on `configured`, and `ejazty://auth/callback` is already allow-listed, so this goes live for every user who takes the easier button the moment one dashboard toggle changes. A gap that opens on a config flip is worse than one that opens on a code change, because nothing in review sees it happen.

  Three things constrain edits:

  - **`hasPassword` is an affordance, not a gate, and must not become one.** It is derived from `session.user.identities` — no round-trip, unlike `reauthenticate`'s deliberate `getUser()` — and it decides what the account screen *offers*, never what the server accepts. That is why it answers **true** on missing evidence: `identities` is absent on a session persisted by an older build, and answering "no password" there would tell an ordinary user their password does not work on the screen where they came to change it. A wrong `true` shows a form that fails, which is the pre-existing behaviour; a wrong `false` would remove a working feature. The forms are still rendered underneath the explanation for the same reason.
  - **The way out is the recovery flow, not a new one.** The screen offers "email me a link to set a password", which is `resetPasswordForEmail` → deep link → `(auth)/reset-password` — already built, already tested, and with the ordinary forgot-password semantics. Once the user returns through it the account has a password and every existing gate applies unchanged, `amr` included. A "set a password here" form was deliberately **not** added: that means `updateUser({ password })` with no proof beyond a live session, which is exactly the borrowed-unlocked-phone hole `reauthenticate` exists to close, and it would be a new auth path with no test behind it added in the change meant to harden one.
  - **The same action is offered to accounts that do have a password**, worded as recovery. Somebody who has forgotten the password the card keeps asking for would otherwise have to sign out to reach the forgot-password screen — signing out of an account they cannot get back into. It also means a wrong `hasPassword` reading leaves a working route rather than a dead end, which is what lets that flag stay an affordance.

  `identities.test.ts` pins the rules and is mutation-checked: making `hasPasswordIdentity` return true unconditionally fails 2.

- **Three operations re-authenticate first, through one shared `features/auth/reauth.ts`.** Supabase's `updateUser` and the `delete_own_account` RPC act on whatever session is stored and never ask for the existing password, so without this an unlocked phone is enough to take or destroy the account. `updatePassword`, `updateEmail` and `deleteAccount` all call `reauthenticate(currentPassword)`, which verifies with `signInWithPassword` against **the account's own email** — it takes no address parameter, because one would let a caller prove the wrong account. Every form clears its password field on success.

  It reads that address with **`getUser()`, not `getSession()`**, and the difference is the point: `getSession` hands back the session as it sits in SecureStore without re-verifying it, so the address this gate checks against would be one an attacker with filesystem access could edit. `getUser` asks GoTrue and reads it off the verified response. The extra round-trip costs nothing — the next line makes a network call anyway.

- **`reauth.ts` closes the borrowed-phone case, not the stolen-token case, and every operation now has a server half too.** It runs in the client, and the client is not a boundary: the anon key ships in the bundle, so an attacker holding a stolen access token posts straight to GoTrue or PostgREST and never executes it. The three server halves:

  | Operation | Server half |
  | --- | --- |
  | `updatePassword` | `auth.email.secure_password_change` in `supabase/config.toml` |
  | `updateEmail` | `auth.email.double_confirm_changes`, same file |
  | `deleteAccount` | the `amr` freshness check inside `delete_own_account()` (`20260804130000_require_recent_reauth.sql`) |

  Neither half substitutes for the other. **If you add a fourth account-mutating operation it needs both** — and if the server half cannot be expressed as GoTrue config, it belongs in the RPC the way deletion's does.

  It is one module rather than three inline blocks for a specific reason beyond drift: it posts to the same `/token?grant_type=password` endpoint as sign-in, so it needs the same CAPTCHA token, and a call site that forgot one would fail with `captcha_failed` while sign-in kept working. Being a module also makes it testable — the provider is a React context and this project has no renderer tests, so a security check reachable only by hand is one that silently stops working. **If you add a fourth account-mutating operation, it calls this too.**

- **`reauthenticate` carries a local backoff: five wrong passwords, then a one-minute lockout, persisted to the keychain.** This is the one place in the project where a *client-side* rate limit is the correct control, and the reason is which attacker it faces. GoTrue's `sign_in_sign_ups` is **per IP and shared with real sign-ins**, so it cannot be tightened for this screen without throttling ordinary people on a shared network, and GoTrue has no per-account lockout at all — which left the account screen accepting ~30 current-password guesses every five minutes, forever, in front of an irreversible delete. Note `passwordProblemKey` deliberately never runs on existing credentials, so the password being guessed may well be a weak legacy one.

  It bounds the borrowed-unlocked-phone attacker, who is driving the app's own UI. It does nothing against someone scripting GoTrue directly — but that person never executes this function anyway, so the two controls cover different attackers rather than duplicating each other.

  Two details that are the whole point: it is **persisted rather than module state**, because in memory a force-quit clears it and that is a bypass anyone holding the phone finds by accident; and only a **correct** password clears the counter, so failures cannot be laundered by interleaving them with something that succeeds. `signOut` calls `clearReauthBackoff()` so a second account on the same device does not inherit a cooldown — not a bypass, since signing back in needs the very password being guessed. It rejects with `over_request_rate_limit`, which `CODE_KEYS` already maps, so it needed no new string in three locales.

  **It moved from AsyncStorage to the keychain on 2026-08-08, and the argument is the force-quit one carried one step further.** AsyncStorage is unencrypted on both platforms and, before `allowBackup: false`, was eligible for Android backup — so restoring a crafted backup reset the counter, which is the *same* bypass persisting it exists to close. It now goes through `readSecureJSON`/`writeSecureJSON` in `lib/secure-storage.ts`, thin JSON wrappers over `SecureStoreAdapter`; wrapping the adapter rather than calling SecureStore directly means a counter written by a previous build is migrated on first read and its plaintext copy deleted, with no migration code of its own. The two controls are not redundant — `allowBackup: false` covers everything in AsyncStorage as a class, this covers the counter even on a device where that data is readable. Residual, stated plainly: a *rooted* device can still clear the keychain item, which matters little because the same person can reinstall the app and reset it by design. `reauth.test.ts` pins the absence from AsyncStorage as hard as the presence in the keychain — a version writing to **both** would pass every other assertion while leaving the bypass open — and is mutation-checked: reverting to `readJSON`/`writeJSON` fails 4.

  The general rule for what belongs in which store, since this is the only entry that has moved: **ask whether restoring an old copy of the value is an attack.** For a study streak or the exam history it is not, and the keychain's per-item syscall is not worth paying on a hot path. For a counter that bounds an attacker it is exactly the attack. `lib/secure-storage.ts` carries the same note.
- **`updateEmail`'s server half is `double_confirm_changes`.** Re-auth stops the change being *started* from an unlocked phone; secure email change makes the *old* address confirm too, which stops it completing if a session was taken some other way. With both off the takeover path is short and complete: move the address to one you control, confirm from your own inbox, then run a password reset. See `supabase/SECURITY.md` §4.2.
- **`updateEmail` does not update local state.** Supabase confirms an address change by mail, so the address on screen must keep showing the old one until the user clicks the link.
- **Account deletion re-authenticates, and the password is collected before the confirm dialog.** The `Alert` is the last thing between the user and an irreversible cascade, so it should not be dismissed only to report an empty field. Deletion is the one operation with nothing to restore from, which is why it is gated at least as hard as a password change rather than by a confirmation tap alone.
- **Account deletion needs a server-side function.** `auth.admin.deleteUser` requires the service-role key, and `EXPO_PUBLIC_` values are inlined into the bundle at build time — shipping it would give every installer a credential that bypasses RLS. The app instead calls the `delete_own_account` RPC in `supabase/migrations/20260803125300_delete_own_account.sql`: a `security definer` function that deletes only `auth.uid()`, so the privilege stays in the database and no parameter can name another user. **Apply that migration or deletion fails with `PGRST202`**, which `authErrorKey` maps to a specific "not set up on the server" message rather than the generic one.

  **`20260804130000_require_recent_reauth.sql` adds the missing half.** The original function checked only that `auth.uid()` was not null, so a stolen access token replayed straight at `POST /rest/v1/rpc/delete_own_account` destroyed the account without ever running `reauthenticate`. It now requires a password to have been presented within the last 300 seconds, read from the JWT's `amr` claim — which `signInWithPassword` refreshes, and which supabase-js carries into the very next request because `accessToken` is resolved per call rather than captured at construction. `amr` is used rather than `iat` because it survives automatic token refresh; `iat` is kept only as a fallback so a project whose JWTs lack `amr` degrades to the weaker check instead of losing account deletion entirely. Changing the window means changing it in one place, but verify by hand: this is the one security check in the project with no test, because it lives in SQL.
- Deleting an account also clears the cached attempts from the device. The server side goes with it — `profiles` and `exam_attempts` both cascade from `auth.users`. Language and theme survive: they are device preferences, not account data.

## The profile picture and the daily goal are device-local, deliberately

Two personal-feeling features that never touch the network. The reasoning is the same for both and it is the app's existing commitments, not laziness: it has to work **offline** and **for guests** — a guest has no account to hang a remote object off — and every server-side store here is reachable with the anon key that ships in the bundle, so a new bucket or table is a new RLS surface to get right. The cost is stated plainly in the UI (`account.photoNotice`) rather than left to be discovered: neither follows the account to a second device, and a reinstall loses both.

**`features/profile/avatar.ts`.** Three things constrain edits:

- **The stored value is a *filename*, never a URI.** The obvious version stores what the picker handed back, which works in testing and fails twice in the field: that URI is in the **cache** directory, which the OS evicts under storage pressure, and the iOS app container path carries a UUID re-minted on reinstall — so a stored absolute URI goes stale while the file it names is still there. The file is copied into the document directory and the URI is rebuilt from `Paths.document` on every read.
- **The filename is minted fresh on every change.** A fixed `avatar.jpg` means `expo-image`'s caches keep serving the previous picture, because the URI has not changed and nothing tells them to reload.
- **The owner rule is the attempts cache's rule.** `ownerId: null` is device-local and adopted by the first account to sign in; a picture owned by a *different* account is never shown. `clearAccountAvatar` on sign-out is asymmetric for exactly the reason `clearAccountAttemptCache` is — an account's picture must not greet whoever signs in next, and a guest's must survive, because signing out is how a guest goes off to register. Account deletion clears unconditionally.

The picker itself is offered to guests too, on the guest branch of the account screen. That is not generosity — without it the `ownerId: null` path is unreachable and the adoption rule is dead code.

**`features/progress/goal.ts`.** A daily target in *questions answered correctly*, not exams finished: "one exam a day" is unreachable on a busy day, trivially met on a quiet one, and makes open practice count for nothing until it is submitted. `recordCorrect` is therefore called from `ExamSessionProvider`'s `answer` handler as each answer lands.

**Only correct answers count, and `goal.ts` is not what decides that.** The module only knows how to add. The rule is `earnsGoalCredit` in **`features/exam/goal-credit.ts`**, called from the runner, which is the only place holding both the question and what the attempt has already paid out for. It is a module rather than three lines inline for the reason everything else here is: both halves fail *silently* — a version crediting every answer is indistinguishable from a learner getting them right — and the runner is a React provider this project cannot render-test. `goal-credit.test.ts` pins it and is mutation-checked: dropping the correctness check fails 1, dropping the per-question cap fails 1.

Three things about the rule:

- **A question credits at most once per attempt**, tracked in a `credited` ref cleared by `start` and `reset`. Answers stay editable in the three non-revealing modes — that is what the question navigator is *for* — so right, wrong, right is ordinary behaviour while checking your work, and without the cap it mints a fresh point every pass.
- **Credit is never taken *back*** when a correct answer is changed to a wrong one. A goal that counts down while you work is one nobody trusts. The accepted cost is that the day's tally is a high-water mark rather than a mirror of the final paper — the result screen reports the score of what was actually submitted.
- **Points cannot be farmed against revealed answers.** `open` is the only mode that reveals as the answer lands, and its choices lock once answered. The lock and the cap cover each other.

**The stored count was renamed `answered` → `correct`, and `parseProgress` still reads the old key.** Not politeness: `rollOver` decides whether a streak survives by comparing the *stored* count against the goal, so a yesterday that suddenly read 0 would silently break the streak of every learner who had one on the upgrade. A legacy record counted every answer, so carrying it forward over-credits the upgrade day — the gentler of the two errors, and in the same direction `rollOver` already errs. Delete `LEGACY_COUNT_KEY` once no shipped build can still hold a pre-rename record.

Two details that are load-bearing:

- **`answer` reads the question and the credit from refs**, not from inside the `setAnswers` updater. That updater is a reducer, React is free to invoke it twice (it does under StrictMode), and a side effect inside it double-counts every answer.
- **The roll-over happens on *read*.** Nothing fires at midnight, so a version that only rolled over on write would show yesterday's count until the learner answered something — and the case that actually happens is the app being backgrounded overnight and foregrounded the next morning.

  **`GoalProvider` therefore re-reads on every foreground, and for a while it did not.** Rolling over on read is only a design if something reads: the provider read once in a mount effect, so the overnight case the rule exists for kept yesterday's tally and yesterday's ring on the Learn hero and in settings until the learner answered a question — at which point `recordCorrect`'s own `readProgress` rolled over and the first answer of the day silently absorbed the whole of yesterday's count. An `AppState` listener rather than a midnight timer, for the reason above: the app is usually not running at midnight. Three async reads now land in the same two pieces of state — the cold start, the foreground refresh, and `record`'s write-then-read — so each claims a monotonic ticket and applies only if nothing newer already has; storage is the source of truth, and the hazard is an *older* read arriving last.

**`settings.haptics` is a real preference, not a filler switch** — the app taps on every answer, option and tab change. `lib/haptics.ts` holds the flag in **module state**, mirrored there by `PreferencesProvider`, because `selectionTap` is called synchronously from event handlers deep inside the exam runner and from `FloatingTabBar`, none of which can subscribe to a context. It defaults to **on**, matching the module default, so the frames before preferences load do not swallow the first tap.

**The haptic vocabulary is five patterns and is deliberately small.** A pattern the user cannot tell from the previous one is not feedback, it is vibration — and a phone that taps at everything trains people to turn the switch off, which loses the three taps that were carrying information. `selectionTap` uses **`selectionAsync`, not `impactAsync(Light)`**: selection feedback is the platform's own idiom for a value changing under the finger, tuned to survive repeat firing, where an impact is a *collision* and heavier than a tab change warrants. `resultFeedback` keeps Success/Error, `goalReachedFeedback` marks the ring filling (the one unprompted haptic in the app — warranted because that ring is on another tab), and `warningFeedback` sits in front of the irreversible ones: quitting a running attempt, signing out, deleting an account.

**`answerFeedback(revealing, correct)` carries a real rule, not a style choice.** Only `open` practice shows whether an answer was right as it lands; a timed mock withholds that until submission, and the withholding is what makes the score mean anything. A haptic that distinguished correct from wrong would hand the answer back through the learner's fingers on every question of every graded paper, **silently** — nothing on screen changes. So the distinction is drawn only where the screen has already drawn it, which is also where it earns its keep, since it lets someone drill without watching the card. The session screen therefore passes `modeReveals` (the mode's own property) rather than `revealing` (which is still false at press time, because nothing has been answered yet).

`lib/haptics.test.ts` pins both that rule and the preference gate, and is mutation-checked: ignoring `revealing` fails 1, ignoring the enabled flag fails 2. The assertions compare *which pattern* reaches the native module rather than a call sequence — the patterns are the vocabulary, and two call sites playing the same one is the failure the vocabulary exists to prevent. The non-revealing case asserts the two branches are **identical to each other** rather than equal to a named pattern, because any difference at all is the leak.

## User data — what is in the database and what is not

The split is deliberate: **study content ships with the app, user data lives in Supabase.**

Signs, questions, rules and dashboard lights stay in `src/content/data/` because the app must be usable offline and by guests, and because a graded attempt must never depend on a network call. Nothing in `src/content/` reads from Supabase.

What *is* in the database (`supabase/migrations/20260803140000_user_progress.sql`):

- **`profiles`** — one row per user, keyed by the auth user id. Holds `display_name` (a queryable mirror of `user_metadata.full_name`, which stays authoritative) and `locale`. Created by an `on_auth_user_created` trigger, so the app never meets a signed-in user without a profile.
- **`exam_attempts`** — one row per graded attempt. RLS on both tables restricts every operation to `auth.uid()`; there is no policy granting `anon` anything.

`20260803160000_harden_exam_attempts.sql` adds the rules the columns could not express individually. Attempts are graded on the device and inserted verbatim, so the database restates two of them: `passed = (percent >= 80)`, and `taken_at` no more than a day ahead of `now()`. Neither is access control — RLS already confines writes to the caller's own rows, so the only history anyone can forge is their own. They are integrity: a future `taken_at` sorts above every real attempt in the newest-first list and poisons the baseline `compareAttempt()` scores against. The migration repairs offending rows *before* adding the constraints, because `add constraint` fails outright on a single violation and would otherwise stop half-applied. `user_id` also gains `default auth.uid()` — defence in depth behind the `with check` policy that already rejects any other value.

`20260804120000_tighten_user_data.sql` adds the cross-column rule the hardening migration left out. Every earlier constraint checks a column against a literal, or `passed` against `percent`; **nothing checked `percent` against `correct` and `total`**, so `correct: 0, total: 30, percent: 100, passed: true` satisfied the entire schema — a zero score stored and rendered as perfect. That matters beyond its own row: `percent` is what the history list, the personal-best tile and `compareAttempt()`'s baseline all read. It also rejects whitespace-only `display_name` and `client_id`, which the length bounds admitted. `isPushable` mirrors both, and `attempts.test.ts` pins the rounding: JS `Math.round` and Postgres `round(numeric)` agree at `.5` for positive values, so client and constraint round identically.

`20260804140000_bound_user_metadata.sql` closes the one client-writable store the bounding migration could not reach. `display_name` and `client_id` live in `public` and take CHECK constraints; **`auth.users.raw_user_meta_data` does not** — it is GoTrue's table, `updateUser({ data })` writes straight into it, and it was unbounded `jsonb`. The app writes a single 80-character key, but the app is not the only caller: one throwaway signup is enough to script GoTrue directly and PUT megabytes of arbitrary JSON into a row that passes every policy in the project. Like the bounding migration, this is an availability and billing bound rather than access control.

It is a **trigger, not a CHECK**, deliberately: a constraint on `auth.users` risks a future GoTrue migration failing against something it knows nothing about, which breaks auth outright, whereas dropping a trigger restores stock behaviour exactly. The shape that matters is the `tg_op` guard — **the check runs only when `raw_user_meta_data` is actually changing.** GoTrue writes to `auth.users` on every sign-in (`last_sign_in_at`), so a check that fired on those would make any account already holding an oversized blob unable to *sign in*, permanently, turning a storage bound into a lockout. `full_name` is truncated rather than rejected, for the same reason `20260803180000` truncates; the size and key-count bounds reject, because there is no meaningful way to shorten arbitrary JSON. The trigger is added to `assert_expected_triggers()` so its absence is caught rather than silent.

`20260804120000` adds **`assert_expected_triggers()`**, the trigger counterpart to `assert_rls_enabled()`. `on_auth_user_created`, `profiles_touch_updated_at` and `exam_attempts_quota` all carry behaviour the app assumes and never checks, and all three are invisible when absent — a missing profile trigger just looks like a profile that never appears. `create or replace function` on a later migration does not restore a dropped *trigger*, and a backup predating one comes back without it. Both assertions run at the end of the push.

**No new indexes, deliberately.** Measured on the live project: `exam_attempts_client_id_unique`, `exam_attempts_user_taken_at_idx` and `profiles_pkey` are all at 100% usage and cover every query the app makes. `exam_attempts_pkey` is at **zero scans** — the uuid PK is dead weight and the natural key is `(user_id, client_id)` — but replacing a primary key rewrites the table, so it is left alone. An index nothing reads is still written on every insert.

`20260803170000_bound_user_input.sql` bounds *size*, which none of the above does. `display_name` and `client_id` were unbounded `text`, and nothing capped how many attempts one account could insert — so "your own rows" was an unlimited number of unlimited-length strings. That matters because the anon key ships in the bundle by design: one throwaway signup is enough to script PostgREST directly and fill the project's storage with rows that pass every policy and every CHECK. The migration adds an 80-char bound on `display_name`, 1–64 on `client_id`, and a `before insert` trigger capping attempts at 2000 per user. **The trigger is `before insert` only** — the push is an upsert on `(user_id, client_id)`, and one landing on an existing row takes the UPDATE path, so re-syncing a device at the cap keeps working. Like the hardening migration, it repairs offending rows first; an over-long `display_name` is truncated (the user chose it) while an over-long `client_id` is deleted, because that column is the dedupe key and a truncated one is a different record, not a repaired one.

### Per-question performance, and why it is aggregated

`features/progress/question-stats.ts` plus `20260808130000_question_stats.sql`. This is what lets the app answer **"which questions do I keep getting wrong?"** — `exam_attempts` stores aggregates only, so before it a learner's mistakes existed solely in memory during the result screen and were discarded on reset. It is what the `drill` format draws from.

Same rule as `attempts.ts`: **local first, push after**, with the same owner boundary (`ownerId: null` is device-local and adopted by the first account to sign in; a record owned by someone else is discarded rather than shown) and the same sign-out asymmetry (an account's record goes, a guest's stays, because signing out is how a guest goes off to register).

**One row per question, not one per answer, and this is the decision to preserve.** The obvious shape is a row per (attempt, question), which keeps full history. It is also unbounded in exactly the way this project already guards against: `open` practice draws the whole bank and `enforce_attempt_quota` permits 2000 attempts, so the ceiling is on the order of a million rows for one account — and the anon key ships in the bundle by design, so one throwaway signup is enough to script PostgREST directly and mint them. Aggregating per question bounds the table by the size of the bank instead, and answers both features it was built for. **The accepted cost, stated rather than buried: an individual past attempt cannot be reconstructed question by question.**

Three things constrain edits:

- **The client sends merged absolute counters, not deltas.** An increment in SQL (`seen = question_stats.seen + 1`) would be wrong: the same attempt can be pushed twice — a retry overlapping a sync, or an attempt recorded offline going up late — and an increment double-counts where an overwrite is idempotent. Same reasoning as `exam_attempts` deduping on `(user_id, client_id)`.
- **`last_correct` is stored, not derived**, and a CHECK ties it to the counters in both directions (never correct yet correct last time; never missed yet wrong last time). The ratio cannot answer "which one was missed" — 3 of 4 does not say — and the drill reads the verdict while the trend reads the ratio.
- **Only answered questions are recorded.** A fixed-length paper grades what time ran out on, correctly, and `ExamResult.skipped` reports it — but a skipped question says nothing about whether the learner *knows* it, and recording a timed-out tail as mistakes fills the drill with material they never saw.

`isPushable` mirrors every CHECK client-side for the reason the attempt version does: the push is one batch upsert, Postgres fails a batch as a unit, and the error is ignored by design.

### The sync layer

`features/progress/attempts.ts` owns all of it. The rule is **local first, push after**: an attempt is written to the cache and rendered before the network is touched, so a failed push costs the learner nothing.

- **`ExamAttemptRecord.id` is minted on the device** and is the `client_id` the remote upsert dedupes on (`unique (user_id, client_id)`). Without it a retry, or an attempt graded offline and pushed later, would appear in the history twice.
- **The cache records its owner.** `{ ownerId, attempts }` — `ownerId: null` means device-local (a guest's, or made before anyone signed in). On sign-in, a `null`-owned cache is **adopted** by that account; a cache owned by *someone else* is discarded before anything is pushed, network or not. That is what stops one person's history being shown to the next account on the same phone.

  **Sign-out clears an *account's* cache and deliberately keeps a guest's** (`clearAccountAttemptCache`). The two arrive through the same button and need opposite answers. An account's attempts are in Supabase by then, and leaving them would show one person's history to whoever signs in next. A guest's exist nowhere else — and `ownerId: null` is precisely the state the adoption rule above exists to pick up, so clearing unconditionally destroyed the practice history of everyone who tried the app before registering, at the moment they went to register. Keeping it gives nothing away: a device-local cache has no account behind it, and a signed-in user still never sees a cache owned by someone else.
- **`syncAttempts` pushes before it pulls,** so offline-graded attempts are already in the merged result. On any network failure it returns the cached list rather than an empty one: being offline must not look like having no history.
- **`isPushable` filters the batch first, and this is load-bearing.** The push is one batch upsert, and Postgres fails a batch as a unit; the error is then ignored by design, because a failed push is meant to cost the learner nothing. Composed, those two facts meant a *single* record the table would reject — a hand-edited cache, a wrong device clock, a record from a build that graded differently — stopped **every** attempt syncing, silently and permanently. `isPushable` restates each CHECK constraint client-side so a bad record costs only itself. It stays in the cache and on screen: it is still the user's result, and deleting their data to satisfy a constraint is the wrong trade.
- **`parseAttemptRow` validates what comes back.** RLS guarantees the rows are the caller's own; it guarantees nothing about their *shape*. The previous `as AttemptRow[]` cast asserted rather than checked, so a renamed column or a drifted projection would reach the results screen as `NaN%`.
- The old storage shape was a bare array with no ids. `readAttemptCache` upgrades it, deriving ids deterministically (`legacyId`) so migrating twice cannot turn one attempt into two.

`ExamSessionProvider` calls this and waits for `auth.ready` first — running earlier reads as "guest" and blanks a signed-in user's history for a frame.

The exam engine is untouched by all of this: it stays pure and never sees the network.
